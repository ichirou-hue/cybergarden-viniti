# AGENTS.md

Хакатон ВИНИТИ РАН / ЮФУ: извлечение проверяемых научных результатов из PDF в связанные CSV.
Две предметные области: `solar` (тонкоплёночные солнечные элементы) и `rag` (системы RAG).

## Состояние репозитория

Ядро бекенда написано и работает для обеих областей:

- `passport.py` -> `passport.json` - схема обеих областей (94 поля solar, 85 полей rag);
- `db.py` - SQLite, таблицы на область, конверт `documents`/`blocks`/`jobs`;
- `import_gold.py` - импорт эталона организаторов как есть, для сверки и для скорера;
- `pdf_source.py` + `extract.py` + `verify.py` - разбор PDF, шов под экстрактор, проверка цитат;
- `issues.py` - находки о несогласованности данных (таблица `issues`);
- `export_csv.py` - официальная выгрузка (байт в байт как эталон) и произвольный срез;
- `batch.py` - пакетный прогон корпуса с очередью задач в `jobs`;
- `pipeline.py` - весь цикл одной командой: разбор -> находки -> CSV -> гейт;
- `server.py` - HTTP API, `serve_data.py` - браузерный просмотр среза через Datasette;
- `solar_offline.py` - детерминированное извлечение области solar прямо в семь CSV
  шаблона участников, без LLM; `solar_facts.py` - контракт кандидатов, проверка цитат,
  нормализация единиц и согласованность, `solar_schema.py` - колонки и словари шаблона;
- `score.py` - precision/recall против эталона, `tools/gate.py` - гейт валидаторов.

Качество извлечения - baseline, а не решение. `extract.TableFiller` берёт только строки
таблиц, которые `pdf_source` уже разложил на ячейки, и только когда шапка с метриками
попала в то же окно. Замер по `solar/dev`: строгий recall 6.6 % (42 строки эталона из 636),
precision 75.0 %, потолок самого метода 67.1 % - остальное лежит в прозе и в рисунках.
Верификатор при этом отклонил 0 кандидатов: канал доказательств работает, вход в него пуст.
Предметные правила извлечения - работа ML-разработчиков области, не бекенда.
Для solar этот филлер больше не путь по умолчанию: он остался запасным вариантом
(`--processor extract:process`) и продолжает обслуживать rag.

Основной путь области solar - `solar_offline.py`: он читает PDF напрямую
(`pdfplumber` для координат слов, `pypdf` для текста цитат), собирает семь таблиц
шаблона и отдаёт их `solar_facts.finalize`, который проверяет буквальные цитаты,
нормализует единицы и запускает детерминированные проверки согласованности.
Модель не используется, поэтому результат воспроизводим. Замер по `solar/dev`
(21 PDF, `score.py`): results F1 0.33, publications 1.00, devices 0.57,
layers 0.34, measurements 0.55, issues 0.48, итого 0.37 на базе после `batch`.
Полный `pipeline` добавляет к 94 находкам экстрактора ещё 4 машинные
`jv_consistency`, поэтому его итог 0.3693 - это не регрессия, а другой набор
находок. Старый путь на том же
наборе и том же скорере даёт 0 совпадений results и не заполняет шесть таблиц
из семи (`extract.run` пишет только results), то есть сдать его нельзя - поэтому
`TableFiller` и переведён в запасной вариант. Провал сосредоточен там,
где значение названо только в прозе или на рисунке: приписать его конкретному
прибору детерминированно нельзя, а непривязанная строка (`result_origin=cited`)
эталонному ключу не соответствует. Это ограничение метода, а не баг.

Старый прототип (`library.py`, `rag_facts.py`, `analyze_pdfs.py`, `demo.py`) покрывал только
`rag` и только 9 метрик из 37 616. Он оставлен ради `test_smoke.py`. Новый код от него
не зависит, и считать его поведение контрактом нельзя.

`python -X utf8` обязателен: в консоли Windows кодировка cp1252, и русский вывод без флага
падает или превращается в мусор. То же касается записи CSV - `export_csv.py` пишет BOM и CRLF
сам, кодировкой консоли это не управляется.

Линтеров, форматтеров и проверки типов в репозитории нет: ни `pyproject.toml`,
ни `ruff`/`flake8`/`mypy`, ни `Makefile`. Не придумывать команды для них.

Тесты импортируют `demo.py`, а он требует `reportlab`. В окружении без
`pip install -r requirements.txt` сборка тестов падает на `ModuleNotFoundError`,
а не на логике - сначала ставьте зависимости. Тесты поднимают настоящий HTTP-сервер
на `127.0.0.1` со случайным портом и ходят в него через `urlopen`.

CI (`.github/workflows/smoke.yml`) гоняет `python -m unittest -v` на ubuntu и windows
под Python 3.12. Локально может быть 3.14 - расхождение версий допустимо, но CI главный.
Тесты не требуют ни `_corpus/`, ни `_refs/`: они строят синтетические PDF через `reportlab`
и временные базы. Всё, что ходит в настоящий корпус, лежит в `tools/` и в `.slim/`.

## Как связан код

```
pdf_source.extract(bytes)            текст страниц (pypdf), таблицы и ячейки (pdfplumber)
  -> extract.context_windows         окна источников с перекрытием
  -> filler.fill(window, spec)       кандидаты; TableFiller - baseline области solar
  -> verify.verify_record            цитата или локатор реально есть на указанной странице
  -> db (таблица <area>_<table>)     только принятые строки, плюс documents и blocks
  -> issues.generate                 находки о несогласованности
  -> export_csv.export_official      CSV области
  -> tools.gate.check                валидатор организаторов
```

`batch.py` крутит эту цепочку по одной публикации и ведёт `jobs`; `pipeline.py` вызывает
`batch.run`, `issues`, `export_csv` и `tools/gate` по очереди на каждую область.
`server.py` и `serve_data.py` читают ту же базу и ничего не пересчитывают.

У области solar основной экстрактор - детерминированный `solar_offline`, а не
`extract.TableFiller`. `batch.py` и `pipeline.py` вызывают его по умолчанию через
`batch.default_process`; RAG по-прежнему идёт через `extract.process`. Есть и короткий
путь без базы, сразу в шаблон участников:

```
solar_offline.build(bytes)           таблицы из координат слов (pdfplumber), проза по строкам
  -> solar_facts.finalize            буквальные цитаты, единицы, проверки согласованности
  -> out/<table>.csv                 семь CSV шаблона, колонки из solar_schema.TABLES
```

В базу пишет `solar_offline.process(area, id, path)` - процессор для `batch.run`:
он заменяет все строки публикации во всех семи таблицах плюс конверт `documents`/`blocks`
(`parser_version = 2`) и возвращает сводку. Ревизия solar берётся из
`solar_offline.PARSER_VERSION` (сейчас 2), иначе `--resume` пропустил бы публикации,
которые старый экстрактор уже пометил `ok` под ревизией 1. `--processor` по-прежнему
перекрывает выбор для точечных экспериментов. Тесты - `test_solar_offline.py`,
синтетические PDF через `reportlab`.

Шов под экстрактор - протокол `extract.Filler` с единственным методом
`fill(window, spec) -> list[dict]`. Кандидат заполняется по `spec["columns"]`, а
`publication_id` и `result_id` проставляет `extract.run`, не филлер. Филлер не пишет
в базу и не имеет права выдумывать `source_page`. Строка, которую не удалось выровнять,
пропускается, а не угадывается.

`verify.py` - точка доверия, и её правила надо соблюдать, а не обходить:

- цитата проверяется как литерал на странице, после нормализации пробелов, переносов
  и дефисов (`compact`);
- локатор (`Table 1, строка pristine`, `Figure 2:`, `TABLE I`) - это ссылка, а не цитата:
  он принимается, если метка есть на указанной странице, и число из `metric_value`
  им не подтверждается;
- `metric_value` должен быть напечатан в цитате, с допуском на масштаб 1/100/1000
  (`0.70` против `70.0 %`, `0.96 V` против `960 mV`);
- пустое `metric_value` допустимо только при `extraction_status` в
  `("present_not_extractable", "absent")`.

Две вещи надо править руками при расширении:

- `passport.json` не пишется вручную: меняй `passport.py` и перегенерируй,
  иначе `passport.py --check` и тесты схемы упадут. Числовые зеркала колонок
  (`<column>_num`) тоже берутся из паспорта - по `fields.*.type == "number"`.
- `server.py`: статика отдаётся из `static/` по расширению, список файлов больше не
  хардкодится. Новый эндпоинт добавляется в `do_GET` явно, общего regex на все
  маршруты статьи (`PAPER`) больше нет для новых путей.

Читающие эндпоинты `server.py`: `/api/passport` (схема, по области и целиком),
`/api/results` и `/api/results.csv` (срез: `col`, `where`, `order`, `limit`),
`/api/issues` (находки, фильтры по точному значению колонки), `/api/stats`
(счётчики по областям и таблицам из паспорта), плюс старый `/api/papers` прототипа.
Ошибка в имени поля или в фильтре - 400 с перечнем допустимых, отсутствие базы - 503.

Ручной этап профилей живёт отдельно от паспорта и базы:

- `profiles_store.py` читает встроенные `profiles/*.json` и пользовательские
  `data/profiles/<id>.json`, проверяет их через `extraction_core.compile_profile`;
  `GET /api/profiles`, `GET|PUT|DELETE /api/profiles/<id>`. Встроенные профили
  перезаписывать и удалять нельзя, для изменения нужна копия с новым id.
- `parse_document.py` - разбор PDF по профилю без LLM: готовит источники, таблицы,
  figures и offline-кандидаты, пишет комплект через `extraction_core.export_result`.
  `POST /api/parse` (PDF + `X-Profile`, `X-Parser`, `X-OCR`, `X-Charts`) запускает
  его фоновым процессом; `GET /api/parse/<id>`, `/result` и `/file/<path>` отдают
  статус, JSON и артефакты. Результат лежит в `data/parses/<id>/`, исходный PDF -
  рядом как `input.pdf`; `job.json` обновляется атомарно.
- Для `--parser docling` сервер запускает отдельный интерпретатор из
  `VINITI_DOCLING_PYTHON` (иначе `sys.executable`). OCR и локальный chart2csv
  требуют установленного Docling/Tesseract и весов моделей; без них job завершится
  ошибкой, а не молчаливым частичным результатом. `VINITI_PARSE_TIMEOUT` задаёт
  лимит секунд на один разбор (по умолчанию 1800).
- Это пока разбор, а не извлечение структуры: LLM-этап и LLM-аудит не подключены.

## Схема БД

Один файл `data/viniti.sqlite3` держит обе области. Таблицы области называются
`<area>_<table>` (`solar_results`, `rag_datasets`, ...) и строятся из `passport.json`.
Ключ везде `(area, publication_id, <key>)`, поэтому `D001` области `solar` и `P001`
области `rag` не пересекаются, даже если бы имена совпали.

Значения всех колонок хранятся текстом. Числовые зеркала (`<column>_num`, а также
`value_num`, `norm_num`, `page_num`) существуют только для фильтрации и сортировки;
источник истины - текстовая колонка, и сравнивать результаты по зеркалу нельзя.

Конверт, общий для областей:

- `documents` - одна строка на публикацию: `sha256`, `title`, `page_count`, `text_chars`,
  `parser_status` (`ok`/`empty`), `source_path`;
- `blocks` - одна строка на страницу с текстом из `pypdf`, чтобы `source_fragment`
  можно было проверить по базе, не открывая PDF;
- `jobs` - очередь пакетного прогона: `status`, `attempts`, `extractor_revision`, `error`.

Плюс `issues` - находки `issues.py`, строки с `C*` идентификаторами; строки, пришедшие
из эталона, остаются с `I*` и не переписываются.

## Данные: два комплекта, имена пересекаются

`_corpus/` (в `.gitignore`) содержит оба комплекта участников:

- `_corpus/area1/` - solar: `dev/` 21 PDF, `dev_gold/`, `test/` 90 PDF, `tools/check_submission.py`
- `_corpus/rag/RAG_ВИНИТИ_участникам_2026-11-20/` - rag: то же плюс `submission_template/schema.json`

`D001` и `P001` существуют в обеих областях с разным содержимым. Любой ключ,
идентификатор или путь обязан включать область. Распаковывать архивы только в разные каталоги.

`_refs/` (в `.gitignore`) - сторонние репозитории для изучения подходов, не зависимость проекта.
Файлы внутри могут содержать чужие `AGENTS.md`; они относятся к своим проектам.

## Валидаторы организаторов

Запускать из корня соответствующего комплекта, иначе относительные пути не найдутся:

```powershell
cd _corpus\area1
python tools\check_submission.py dev_gold dev

cd _corpus\rag\RAG_ВИНИТИ_участникам_2026-11-20
python tools\check_submission.py dev_gold dev --json-report report.json
```

Коды выхода различаются между областями:

- `area1` возвращает только `0` или `1` (`return 1 if errors else 0`). JSON-отчёта нет,
  итог приходится разбирать из stdout: `таблиц: N, результатов: N, ошибок: N, предупреждений: N`.
- `rag` возвращает `0`, `1` или `2`, где `2` значит «структурно чисто, но есть цитаты,
  требующие ручной проверки». Есть `--json-report`, `--template`, `--ocr`.

`tools/gate.py` прячет эту разницу: `--area all` прогоняет обе области и возвращает
`0` (структурно чисто), `1` (структурные ошибки) или `3` (гейт сам не отработал).
Различие «чисто» и «чисто, но требует ревью» печатается, но в код выхода не входит.
Области `rag` нужен `pypdf`; `--ocr` дополнительно требует установленный Tesseract.

**Это не скорер.** Валидатор не открывает `dev_gold`, когда проверяет вашу сдачу:
он сверяет ваш набор с самим собой, со схемой и с текстом PDF. Точность и полноту
он не измеряет и в отчёте прямо пишет `semantic_completeness_certified: false`.
Прогон эталона области `rag` против самого себя даёт 0 ошибок и 1187 нерешённых цитат.
Точность и полноту меряет отдельный `score.py`.

## Ловушки данных

- `metric_value` хранить текстом. В области `rag` у 7451 из 37 569 значений текст меняется
  при записи во `float` (`'0.330'` -> `'0.33'`), а валидатор сравнивает дубли по точности.
- `raw_value` в области `rag` на 83 % не число (`↓18.4%`, `EM decrease`) - числовой столбец его не примет.
- Не склеивать результаты по совпадению числа. В `D001` области `rag` 61 пара
  «метрика + значение», где одно число встречается у разных конфигураций; ключ обязан
  включать `config_id`, `dataset_id`, `task_id`. В `solar` то же с `device_id`,
  `measurement_id`, `aggregation`, `time_point`.
- Единицы несовместимы как строки: `1000 W/m2` и `100 mW/cm2` - одна освещённость.
  Сравнение условий возможно только после нормализации (`norm.py`).
- `MAX_BYTES = 20 МиБ` (`library.py:12`, дублируется в `server.py`), но в корпусе есть
  `area1/test/P042.pdf` (25.1 MiB) и `rag/test/P058.pdf` (26.9 MiB). Их надо обрабатывать.
- Ревизия экстрактора: `extract.PARSER_VERSION` и `jobs.extractor_revision`. `batch --resume`
  пропускает публикацию, если `status = ok` и ревизия совпала. Поменял извлечение -
  подними ревизию, иначе старые строки останутся как есть. У solar своя ревизия
  `solar_offline.PARSER_VERSION = 2`, у rag - `DEFAULT_EXTRACTOR_REVISION = 1`.
- `solar_offline` нумерует приборы позиционно (`DV1`, `DV2`, ...; `DV-<slug>` при явном
  коде в названии), а id эталона выбраны людьми и несогласованно (`DV-0`, `DV-R200`,
  `DV0`/`DV40` для содержания Ge). Совпадение id не измеряет качество извлечения:
  сравнивать надо значения и число строк (`score.py` без ключа прибора), иначе
  заниженный recall говорит о нумерации, а не о пропущенных данных.
- `solar_offline` читает таблицу по координатам слов, поэтому страница, где таблица -
  единственный широкий элемент, может распасться на две колонки (`_gutter` видит
  общий разрыв в большинстве строк). Обычный текст над таблицей перекрывает разрыв
  и держит страницу одноколоночной; синтетические фикстуры без абзаца текста
  воспроизводят именно этот крайний случай.
- Старый экстрактор (`extract.run`) удаляет только свои строки `X[0-9][0-9][0-9]`,
  поэтому эталон (`R001`) и извлечение могут лежать в одной таблице и давать дубли.
  `solar_offline.process` удаляет все строки публикации во всех семи таблицах и
  пишет свой набор `R...`, но отказывается работать, если у публикации
  `documents.parser_status = 'imported'`: иначе он молча стёр бы эталон. В общей
  базе такой прогон даёт `jobs.status = error` с объяснением; для сравнения
  с `dev_gold` всё равно нужна отдельная база.
- `solar_offline.process` пишет `documents.year` и `in_scope` из извлечённой строки,
  а `parser_status` всегда `ok`: `prepare_pdf` уже отказал бы PDF без текстового слоя.
  `blocks` - по одной строке на страницу pypdf, как у старого экстрактора.
- `batch --limit N` ограничивает число файлов, реально обработанных за запуск,
  уже после пропуска готовых по `--resume`: повторный `--limit 2 --resume` возьмёт
  следующие два, а не первые два. Для смоук-прогона на чистой базе это первые N.
- `scan_direction` у измерения заполняется только при свидетельстве: слово
  reverse/forward или метка строки `FB-SC`/`SC-FB`. Направление, названное в таблице,
  получает отдельную строку измерения; иначе было бы чужое условие.
- `bandgap` ищется по тексту, но сравнения (`wide bandgap`, `higher than`,
  `larger than`, `above N`) пропускаются: это порог широкозонного слоя, а не
  ширина запрещённой зоны поглотителя.
- `Library.ingest` возвращает уже сохранённую запись, если `sha256` совпал
  (`library.py:71`): файл с тем же содержимым не переразбирается, даже если изменился
  экстрактор. Это старое хранилище, новый код его не использует.
- `analyze_pdfs.py` открывает выходной файл в режиме `"x"` (`analyze_pdfs.py:21`),
  поэтому повторный запуск с тем же `-o` падает, а не перезаписывает результат.
- `pdfplumber` разрывает предложение на подстрочных индексах (`J` / `SC`) и перемешивает
  колонки, поэтому цитаты проверяются по тексту `pypdf` (`pdf_source.page_texts`),
  а не по `pdfplumber`. Один остаточный артефакт (`mA/cm/C02` в D003) так и не сходится.
- `pdf_source.find_tables` на `solar/dev` находит 79 таблиц, из них 43 пустые:
  `extract()` возвращает строки без единой непустой ячейки. Пустые боксы крошечные
  (0-4 % площади страницы), то есть это фантомы детектора, а не таблицы. Филлер
  такие пропускает, но считать «79 таблиц» сырьём нельзя - реальных 36.
- У `D002`, `D013`, `D021` есть страницы без текстового слоя (1028 строк, 2.7 %);
  без OCR они недостижимы, и это надо писать в отчёте, а не замалчивать.

## Документация

`docs/` писалась как раздаточная папка для Google Drive, а не для этого репозитория:
она утверждает, что код клонируется отдельно, хотя `D:\sfedu` и есть этот репозиторий.
Полезное там - `docs/requirements/2026-11-20-hackathon-case-analysis.md` и
`docs/2026-11-20-team-start.md` (распределение ролей).
`docs/materials/*.zip` дублируют `_corpus/` (~745 MiB) и не должны попасть в git.

Рабочие заметки по бекенду, замеры и разборы лежат в `.slim/deepwork/viniti-backend-core/`
(`domain-notes.md` - проверенные факты о данных со ссылками на SQL, `e2e-solar.md` - замер
baseline). Это не документация продукта, но там записано то, что дорого перепроверять.

## Совместная работа

`static/app.js`, `static/index.html`, `static/style.css` - общие файлы, их правки
координируются одним человеком. Предметные правила извлечения принадлежат ML-разработчикам
области, а не backend.
