# CyberGarden · ВИНИТИ РАН

Локальный прототип для направления «RAG и поиск по документам». Загрузите научную статью, найдите метрику и откройте страницу с подсвеченным источником. JSON сохраняет исходную цитату, значение и координаты для последующей обработки.

## Запуск

Приложение состоит из Python-бэкенда и статического фронтенда. Фронтенд собирать не нужно: это ES-модули в `static/`, которые отдаёт тот же Python-сервер. Node.js требуется только для UI-тестов, для запуска приложения он не нужен.

Нужен Python 3.12 с модулями `pip` и `venv`. На Linux их можно установить через пакетный менеджер дистрибутива.

### Установка (один раз)

Linux и macOS:

```bash
git clone https://github.com/ichirou-hue/cybergarden-viniti.git
cd cybergarden-viniti
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Windows (PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Для клонирования нужен доступ к приватному репозиторию. Если Python 3.12 установлен под именем `python3`, проверьте версию через `python3 --version` и используйте этот исполняемый файл. После установки пакетов и первоначального скачивания модельных весов Docling разбор работает локально.

### Бэкенд

`server.py` — продуктовый сервер: принимает PDF, запускает извлечение, хранит результаты в SQLite, отдаёт страницы PDF и статику фронтенда.

```bash
.venv/bin/python server.py
```

- адрес: [http://127.0.0.1:8765](http://127.0.0.1:8765)
- база: `data/papers.sqlite3`, создаётся автоматически
- порт и путь к базе: `--port 8813`, `--db /tmp/papers.sqlite3`
- остановка: `Ctrl+C`

Здесь работают загрузка и разбор PDF, каталог `/#/`, карточка статьи `/#/doc/…` и экран паспорта `/#/passport`. Каталог и карточку наполняет RAG-модуль `rag/` через `/api/documents…` (контракт `docs/adr/0008-rag-catalog-ui.md`); результаты хранятся в той же SQLite-базе.

### Ручной этап профилей

Текущий завершённый этап - распознавание текста и формул: порядок блоков/колонок,
OCR, нижние и верхние индексы, сохранение источников с координатами. Проверен полный
прогон D001 через сайт, включая `SrCl₂-doped CsPbI₂Br` на первой странице.

Следующий этап передаётся разработчикам таблиц и графиков. В `docling_source.py` уже
есть базовые таблицы и вырезки рисунков в `parser_output`, но ещё нужно довести
геометрию ячеек, заголовки/объединения, связи рисунков с подписями и передачу структуры
в интерфейс. Chart2CSV по умолчанию выключен; оцифровка графиков и её качество не
подтверждены. Смысловое связывание научных фактов через LLM - отдельный последующий этап.

Предлагаемое разделение готовых компонентов для следующего этапа:

| Содержимое | Основной компонент | Когда нужен OCR или vision |
|---|---|---|
| Текст, колонки и порядок чтения | Docling layout + PDF backend | Tesseract для сканов и областей без текстового слоя |
| Формулы и индексы | Docling CodeFormulaV2 + ScriptPositionOptions | Локальная модель читает вырезку формулы; индексы текста восстанавливает штатный этап Docling |
| Таблицы | Docling TableFormer в режиме ACCURATE | OCR ячеек для сканов; сохранить ячейки, spans и заголовки, а не только строки CSV |
| Графики | Docling chart enrichment / Granite Vision Chart2CSV | Vision читает изображение графика; серии и значения сохранять как требующие проверки |

Парсер структуры определяет блоки, OCR читает символы из изображений, vision-модель
распознаёт специальное визуальное содержимое. Это разные стадии, а не взаимоисключающие
варианты. При подтверждённых ошибках таблиц/графиков можно сравнить с
[PaddleOCR PP-StructureV3](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html)
на той же небольшой выборке. Параллельный запуск нескольких движков на каждом документе
не требуется до такого сравнения. Параметры основного стека:
[Docling TableFormer](https://docling-project.github.io/docling/usage/advanced_options/),
[Docling chart extraction](https://docling-project.github.io/docling/reference/pipeline_options/).

На `/manual-profile` загрузка PDF автоматически запускает локальный Docling: OCR,
определение порядка блоков, распознавание формул и восстановление нижних/верхних индексов.
Тот же разбор запускается при загрузке Solar в основной каталог; интерфейс ждёт его завершения.
Связи между научными результатами через LLM на этом этапе не строятся. Для распознавания ключ OpenRouter не нужен.

Установите `requirements-docling.txt` и Tesseract с языком `eng`. При первом разборе скачиваются
модельные веса; сервер хранит их в `data/solar/docling-models` (либо каталоге `HF_HOME`).
`VINITI_DOCLING_PYTHON` позволяет использовать отдельное окружение Python. Ошибки моделей/OCR
показываются явно. Для простого локального разбора API поддерживает `X-Parser: pdfplumber`.

Экран ручного профиля - `/manual-profile` (`static/manual-profile.html` и `static/profile.mjs`). На нём выбирают PDF, описывают типы сущностей и поля, отмечают найденные фрагменты и скачивают JSON профиля вместе с доказательствами. PDF уходит на `POST /api/parse`: страница ждёт завершения фонового разбора и берёт страницы и фрагменты из его результата; готовый профиль собирается в браузере. Из мастера загрузки на каталоге выбранный PDF передаётся на этот экран через IndexedDB, поэтому выбирать файл повторно не нужно.

Помощник по полям на этом экране использует `POST /api/profile/assist`. Для него на сервере нужны переменные окружения `OPENROUTER_API_KEY` и `OPENROUTER_MODEL`. Сервер отправляет провайдеру вопрос, названия уже введённых полей и ограниченный набор текстовых фрагментов PDF. Ответ проходит проверку формата и цитат. Предложенные поля и примеры значений добавляются в профиль только после выбора чекбоксов пользователем. Если переменные не заданы, форма ручного ввода продолжает работать, а помощник показывает причину недоступности.

Серверная часть ручного профиля:

- `GET /api/profiles`, `GET|PUT|DELETE /api/profiles/<id>` - встроенные `solar`/`custom-example` и пользовательские профили в `data/profiles/`;
- `POST /api/parse` - PDF и заголовки `X-Profile`, `X-Parser` (`pdfplumber` или `docling`), `X-OCR`, `X-Charts`; разбор идёт в фоне;
- `GET /api/parse/<id>`, `/result`, `/file/candidates.csv`, `/file/assets/...` - статус, JSON и артефакты.

Это распознавание без смыслового связывания фактов, без LLM: текст, таблицы, figures и offline-кандидаты. Для OCR и локального chart2csv задайте `VINITI_DOCLING_PYTHON` на Python с `requirements-docling.txt`; без Docling работает `pdfplumber`. Экран профиля доступен по `/manual-profile`.

### Фронтенд

Отдельного dev-сервера и сборки нет. Фронтенд — это `static/index.html` и модули `static/*.js`; он открывается с того же адреса, что и API, поэтому CORS не нужен.

Экраны:

- `/#/` - главный экран: мастер загрузки PDF и единственное место, где выбирается профиль обработки (RAG или Solar); сюда ведут логотип и любой возврат на главную;
- `/#/catalog?track=rag` - каталог публикаций (из меню аккаунта);
- `/#/doc/<document_id>?track=rag` - карточка статьи, например `/#/doc/rag:d020?track=rag`;
- `/#/passport` - паспорт статьи: импорт JSON, фильтры, CSV, привязка PDF; единственный пункт в верхней навигации;
- `/#/profile` - профиль аккаунта.

#### Вход и профиль

При первом заходе открывается экран регистрации (`static/auth.js`, `static/auth.css`, фон `static/assets/auth-bg.svg`). Аккаунт проверяет сервер: `auth.py` хранит в SQLite только PBKDF2-хэш пароля, выдаёт HttpOnly-cookie сессии и CSRF-токен. Вход выполняется по рабочему email, который служит логином. Гостевого входа больше нет: каталог и загрузка требуют сессию.

После входа `GET /api/auth/me` возвращает пользователя и CSRF-токен; фронтенд повторяет его в заголовке `X-CSRF-Token` у каждого изменяющего запроса. Каталог, карточка и `/api/jobs` фильтруются по владельцу: чужие загруженные документы отвечают 404, а общий демо-документ `rag:demo` видят все, кто вошёл. Истёкшая cookie превращает изменяющий запрос в 401, и интерфейс возвращает экран входа; чтение каталога без сессии отдаёт пустой список.

Поповер в правом верхнем углу (`static/account.js`) ведёт в каталог, профиль и настройки и завершает сессию. В браузере под id пользователя лежат только описательные поля профиля (имя, организация, роль, описание, настройки и лента), а не пароль. Выход завершает серверную сессию, но не удаляет эти поля: повторный вход с тем же email возвращает историю и настройки. Если браузер запрещает `localStorage`, сессия работает, а поля профиля живут в памяти вкладки до перезагрузки.

Каталог и карточка работают на штатном `server.py`: API реализован в `server.py` + `rag_api.py` поверх пакета `rag/`. `tools/mock_api.py` остаётся для разработки и демонстрации контракта без загрузки PDF.

```bash
.venv/bin/python tools/mock_api.py --port 8799
```

Откройте [http://127.0.0.1:8799](http://127.0.0.1:8799). Данные мока детерминированные и хранятся в памяти: перезапуск возвращает исходное состояние.

Каталог, карточка и настоящий разбор PDF работают и на одном `server.py` (8765): загруженный PDF проходит через `rag.extract`, результат сохраняется в SQLite, а `/api/jobs` показывает сводку по загруженным документам.

#### Что где работает

| Возможность | `server.py` (8765) | `mock_api.py` (8799) |
| --- | --- | --- |
| Загрузка и разбор PDF | да, RAG-экстрактор | нет, только демо-кнопка |
| Каталог `#/` | да, по загруженным PDF | да, 8 фикстур |
| Карточка статьи `#/doc/…` | да | да |
| Паспорт `#/passport` | да | да |

Каталог, карточка и паспорт — один интерфейс (`static/index.html` и общий `static/style.css`: тёмная тема, лаймовый акцент, крупный герой — визуал ветки `dev`). JSON паспорта импортируется в браузере кнопкой **Импорт паспорта JSON** и на сервер не уходит; CSV собирается только из прошедших проверку строк, к выбранной публикации можно привязать локальный PDF. Если в импорте нет `validation_status`, статус выводится из данных: замечания → «На разборе», успешное извлечение без замечаний → «Пройдена» (с пометкой, что проверка не запускалась), иначе → «Ожидает». Поддерживаются общий JSON с `results`, экспорт RAG с `facts` и семь таблиц Solar (`static/solar.mjs`). Большие паспорта показываются окнами по 200 строк с кнопкой «Показать ещё». Отдельные `solar.html`, `solar.css` и `solar-ui.mjs` из `dev` больше не нужны: их разметка и логика перенесены в `static/passport.js`.

### Пакетный разбор

```bash
.venv/bin/python analyze_pdfs.py articles/*.pdf -o results.jsonl
```

В PowerShell используйте `.\.venv\Scripts\python.exe` и укажите PDF отдельными аргументами. Пакетный разбор работает без сервера. Он записывает по одному JSON-объекту на успешно разобранный PDF в новый файл. Ошибки выводятся в stderr, а итоговый код 1 означает, что часть входных файлов обработать не удалось. В новых результатах есть SHA-256 исходного PDF и версия извлечения в `extraction`.

## Сценарий демонстрации

### На реальном сервере

1. Запустите `server.py` и откройте [http://127.0.0.1:8765](http://127.0.0.1:8765).
2. Нажмите **Демо** — статья разберётся RAG-экстрактором и появится в каталоге.
3. Откройте карточку: на вкладке **Результаты** видны `Recall@5` и `Recall@10` по конфигурациям.
4. Нажмите **Стр. 1** — откроется PDF с подсветкой строки; **Заголовок** — подсветка подписи таблицы.
5. Проверьте вкладки **Сущности**, **Замечания**, **Фрагменты PDF**, **Сводка** и выгрузку **CSV/JSON**.
6. Загрузите свой PDF кнопкой **Загрузить PDF** — он пройдёт тот же конвейер и сохранится в `data/papers.sqlite3`.

### На моке (богатые фикстуры)

1. Запустите `tools/mock_api.py` и откройте каталог: 8 публикаций, статусы «обработано», «частично», «в очереди», «ошибка», баннер пакетного прогона.
2. Откройте **D020**. На вкладке **Результаты** найдите `Recall`, включите **Только с замечаниями** — останутся строки с проверками.
3. Нажмите **Стр. 5** — откроется страница PDF с подсветкой; кнопка **Заголовок** подсвечивает заголовок таблицы, из которого взята единица.
4. Откройте вкладку **Замечания**, прочитайте причину и нажмите **R001** — таблица вернётся к записи с подсветкой строки.
5. Проверьте **D014** — 28 649 результатов листаются страницами по 50 без загрузки всего конверта.
6. Откройте **D013** — скан без текстового слоя: интерфейс объясняет, что OCR не выполнялся.
7. Выгрузите **CSV (область)** из шапки карточки или из каталога.

## Как устроен прототип

- `pdf_source.py` извлекает текст, строки таблиц и их ячейки. Сохраняет цитаты, страницы и прямоугольники. Для таблиц с горизонтальными линиями использует дополнительную эвристику по выравниванию столбцов.
- `rag_facts.py` распознаёт Recall, Precision, nDCG, MRR, MAP, Hit Rate, Exact Match, F1 и Accuracy. Извлекает k, переводит явно указанные проценты в доли и отмечает неизвестную шкалу для значений выше 1 без единицы. Проверяет диапазон, несовпадающие значения одной метрики и убывание Recall при росте k. Последние две проверки применяются внутри одной строки таблицы.
- `library.py` сохраняет PDF и JSON в одной транзакции SQLite. SHA-256 позволяет повторно загрузить тот же PDF без дубля.
- `server.py` обслуживает загрузку, каталог и карточку `/api/documents…`, экспорт и изображения страниц.
- `rag_api.py` — адаптер между `rag/` и веб-контрактом: прогоняет экстрактор по загруженному PDF, собирает сущности, результаты, замечания и якоря, хранит конверты в SQLite.
- `rag/` — детерминированный RAG-экстрактор: метаданные, таблицы из координат слов, словари метрик и наборов, проверки согласованности и CLI (`python -m rag`).
- `static/` — единый фронтенд без сборки и внешних зависимостей: `catalog.js`, `document.js`, `evidence.js`, `passport.js`, `tracks/rag.js` и общий `style.css`.
- `tools/mock_api.py` — заглушка API и статики для каталога: контракт `docs/adr/0008-rag-catalog-ui.md`, детерминированные фикстуры (обычная статья, скан, 28 649 строк, ошибка загрузки).

В JSON `sources` содержит фрагменты, `facts` содержит метрики и ссылается на фрагменты через `source_id`. Поле `evidence` указывает на линию текста или ячейку со значением. Поле `header` включает ячейку с названием метрики и единицей, когда они взяты из таблицы. `bbox` хранит `[left, top, right, bottom]` в PDF-пунктах от верхнего левого угла страницы, нумерация страниц начинается с 1.

## Охват текущей версии

Поддерживаются PDF с текстовым слоем до 20 МиБ и 150 страниц. Для сканов выводится предупреждение. Формулы и подписи распознаются эвристически и выдаются как цитируемые фрагменты. OCR, оцифровка кривых с графиков, многоуровневые заголовки таблиц и извлечение произвольных утверждений вне набора метрик входят в следующий этап. Проверки выявляют формальные несоответствия. Точность и полнота на корпусе организаторов ещё требуют оценки.

Методика опирается на [документацию pdfplumber по извлечению текста и таблиц](https://github.com/jsvine/pdfplumber#extracting-tables) и [BEIR как пример использования nDCG@k, Recall@k и других метрик поиска](https://arxiv.org/abs/2104.08663).
