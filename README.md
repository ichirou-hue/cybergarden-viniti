# ВИНИТИ РАН / ЮФУ: проверяемые научные результаты из PDF

Конвейер превращает научные PDF в связанные CSV двух предметных областей:
`solar` (тонкоплёночные солнечные элементы) и `rag` (системы поиска и RAG).
Каждая строка результата несёт страницу и цитату, по которой её можно проверить
в исходном PDF, а не только число.

## Быстрый старт

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -X utf8 import_gold.py --area all      # эталон организаторов в базу
.\.venv\Scripts\python.exe -X utf8 pipeline.py --area all --out out
```

`pipeline.py` проходит весь цикл на каждую область: разбор PDF -> находки о
несогласованности -> выгрузка CSV -> валидатор организаторов. Итоговая строка выглядит так:

```
итог: solar=clean, rag=clean but needs review -> exit 0
```

Коды выхода: `0` структурно чисто, `1` структурные ошибки валидатора, `2` были
ошибки разбора при чистом гейте, `3` гейт или конвейер не смог отработать.

`-X utf8` обязателен: консоль Windows по умолчанию в cp1252, и русский вывод без
флага падает или превращается в мусор.

## Что где лежит

| Файл | Роль |
|---|---|
| `passport.py` -> `passport.json` | схема обеих областей: таблицы, колонки, типы, единицы |
| `pdf_source.py` | PDF -> текст страниц (pypdf), таблицы и ячейки (pdfplumber), рендер страницы |
| `extract.py` | окна контекста, шов под экстрактор, запись только проверенных строк |
| `verify.py` | точка доверия: цитата или локатор действительно есть на указанной странице |
| `filler_rag.py` | baseline-экстрактор области `rag` поверх таблиц |
| `issues.py` | находки о несогласованности: единицы, баланс J-V, пропущенные условия |
| `db.py` | SQLite: таблицы `<area>_<table>`, конверт `documents`/`blocks`/`jobs` |
| `import_gold.py` | импорт эталона как есть, для сверки и для скорера |
| `export_csv.py` | официальная выгрузка (байт в байт как эталон) и произвольный срез |
| `batch.py` | пакетный прогон корпуса с очередью задач и `--resume` |
| `pipeline.py` | весь цикл одной командой |
| `score.py` | precision/recall против эталона: это скорер, а не валидатор |
| `tools/gate.py` | единый гейт по валидаторам обеих областей |
| `server.py` | HTTP API: схема, срез, CSV, находки, счётчики |
| `static/` | конструктор выгрузки: выбор области, таблицы, колонок, фильтров |

## Как получить свою выгрузку

Веб-интерфейс:

```powershell
.\.venv\Scripts\python.exe -X utf8 server.py --data data\viniti.sqlite3
# http://127.0.0.1:8765
```

Конструктор строит список колонок из схемы, даёт выбрать область, таблицу, колонки,
фильтры и сортировку, показывает результат и скачивает ровно этот срез.
`source_page` и `source_fragment` снять нельзя: значение без указания, откуда оно,
доказательством не является.

То же из командной строки:

```powershell
.\.venv\Scripts\python.exe -X utf8 export_csv.py --area rag --out slice.csv ^
    --columns metric_name,metric_value,config_name --where "metric_value>20" --limit 500
```

Две выгрузки различаются и смешивать их нельзя:

- **официальная** (`pipeline.py`, `export_csv.py --out <каталог>`) - полная схема,
  порядок колонок из паспорта, BOM и CRLF как в шаблоне организаторов. Именно её
  принимает валидатор.
- **срез** (`--columns`, `--where`, `--order`, `/api/results.csv`) - то, что выбрал
  пользователь. Валидатор его не примет, и это нормально: срез нужен для анализа.

## Проверка

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest -v            # весь набор
.\.venv\Scripts\python.exe -X utf8 passport.py --check       # схема не устарела
.\.venv\Scripts\python.exe -X utf8 tools\gate.py --area all --submission out
.\.venv\Scripts\python.exe -X utf8 score.py --area solar --pred out\solar --ref _corpus\area1\dev_gold
```

Валидатор организаторов - это гейт, а не скорер: он не открывает `dev_gold`, сверяет
сдачу с самой собой, со схемой и с текстом PDF, и прямо пишет
`semantic_completeness_certified: false`. Точность и полноту меряет `score.py`.

## Что уже сделано и что нет

Сделано: схема обеих областей, база, импорт эталона, официальная выгрузка
(14 из 14 таблиц совпадают с эталоном байт в байт), проверка цитат, находки о
несогласованности, пакетный прогон с `--resume`, гейт, скорер, HTTP API и конструктор
среза, 192 теста.

Не сделано, и это главное ограничение: **качество извлечения**. Baseline-экстракторы
читают только строки таблиц и только когда шапка с метриками попала в то же окно.
Замер по `solar/dev`: строгий recall 6.6 %, precision 75.0 %, потолок самого метода
67.1 % - остальное лежит в прозе и в рисунках. Для области `rag` 75.7 % строк эталона
находятся в рисунках и требуют оцифровки, 2.7 % страниц вообще без текстового слоя
(нужен OCR). Предметные правила извлечения - работа ML-разработчиков области.

## Данные

Корпус организаторов лежит в `_corpus/` и в git не попадает: `_corpus/area1/` для
области `solar`, `_corpus/rag/RAG_ВИНИТИ_участникам_2026-11-20/` для `rag`.
Идентификаторы пересекаются между областями (`D001` есть в обеих), поэтому любой ключ
включает область.

`_corpus/` и `_refs/` нужны только для прогона по настоящему корпусу. Тесты их не
требуют: синтетические PDF строятся через `reportlab`, базы - во временных каталогах.

Подробности о данных, ловушках и о том, как связан код, - в `AGENTS.md`.
