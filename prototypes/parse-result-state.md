# Прототип: экран разбора PDF, состояния результата

Текстовый UI-прототип для `static/parse.js`. Не production UI: здесь зафиксированы
места блоков, источник каждого значения и итоговые формулировки. Реализация обязана
брать данные только из уже существующих ответов сервера.

## Задача

Сейчас `status=ok` читается как «готово, данные проверены»: зелёный бейдж «Готово»,
lede «Результат и проверенная интерпретация готовы», заголовок «Проверенные данные».
Для области Solar это неверно: детерминированный экстрактор собирает кандидатов,
полнота не измеряется, часть публикаций вне области, а научные таблицы могут быть пусты.

Нужно, чтобы экран говорил: обработка завершена, но научный результат не подтверждён
как полный, кандидаты не официальная выгрузка, документ может быть вне области Solar.

## Источники данных (ничего не выдумывать)

| Блок | Поле ответа | Что берём |
| --- | --- | --- |
| Статус задания | `GET /api/parse/<id>` -> `status`, `summary`, `llm` | техническое состояние |
| Покрытие | `GET /api/parse/<id>/file/result.json` -> `coverage` | `status`, `completeness`, `reason` |
| Кандидаты | тот же `result.json` -> `candidates[]` | `status`, `context_status`, число строк |
| Научные таблицы | `.../file/llm/interpretation.json` -> `tables` | строки `materials`, `devices`, `layers`, `measurements`, `results` |
| Область | `interpretation.json` -> `tables.publications[]` | `in_scope`, `exclusion_reason` |
| Стадии | `.../llm` (манифест) | `stages`, `counts` |

`result.json` в режиме scripts не содержит научных таблиц (`tables` пуст) и не содержит
подтверждённых записей. Это паспорт разбора плюс кандидаты, и подпись не должна
обещать больше.

Если `result.json` не загрузился, показываем `summary` задания и честную пометку,
что покрытие и статусы кандидатов недоступны.

## Правило области (`in_scope`)

Область считается известной только по явному значению `in_scope`:

- `"true"` - публикация в области;
- `"false"` - вне области, причина из `exclusion_reason`;
- пусто, `null` или незнакомое значение - область **не определена**.

Пустое или незнакомое поле никогда не читается как «в области». Иначе строка без
`in_scope` молча попадала бы в область и завышала картину.

| Данные `publications[]` | Подпись карточки | Баннер |
| --- | --- | --- |
| все `"true"` | В области | нет |
| все `"false"` | Вне области | «Вне области Solar» + причина |
| есть `"false"` и `"true"` | Часть вне области | «Часть публикаций вне области Solar» + причина |
| есть явные значения и пустые | Определена не полностью | нейтральный: для N публикаций область не указана |
| ни одного явного значения | Не определена | нет |
| строк `publications` нет | Не определена | нет |

В таблице публикаций `in_scope` показывается словами: «В области», «Вне области Solar»,
«Не указана». Сырые `true`/`false` и прочерк вместо области не остаются.

## Каркас экрана (сверху вниз)

```
[hero]
  Каталог / Разбор PDF
  <имя файла>
  Разбор документа
  <lede по состоянию>
  [бейдж статуса]            [Скачать файл разбора]

[notice об ошибке, если status=error]

[notice про API / mock, если llm != off]

[panel: Что получено]            <- НОВЫЙ блок
  Обработка файла завершена. Это технический статус разбора, а не подтверждение
  полноты и точности научных данных.
  [Научные записи] [Кандидаты] [Область документа] [Полнота]
  <причина покрытия из coverage.reason>
  <пояснение, если result.json недоступен>

[notice: Кандидаты не подтверждены, если кандидатов > 0]   <- НОВЫЙ блок

[parse-layout: Параметры разбора | Работа модели]

[panel: Интерпретация]           <- уточнённые подписи и пустые состояния
  eyebrow: Черновик модели
  [баннер "Вне области Solar" + причина, если in_scope=false]
  [notice "Научные записи отсутствуют", если научных строк 0]
  <таблицы или пустое состояние>

[panel: Файлы результата]        <- без изменений, ссылки на артефакты
```

Маршрутизация не меняется: `#/parse/<id>` остаётся единственным входом, все ссылки
на `result.json`, `candidates.csv`, `parser.json` и `llm/*` сохраняются.

## Состояние 1: технический `status=ok`, LLM выключен

Данные: `status=ok`, `llm=off`, `summary.candidates=12`, `result.coverage.completeness=not_measured`,
`result.tables` пуст.

```
Разбор документа
Файл обработан. Завершение обработки не подтверждает полноту и точность научных данных.

[Разбор завершён]  [Скачать файл разбора]

Что получено
Обработка файла завершена. Это технический статус разбора, а не подтверждение
полноты и точности научных данных.

  Нет           12                    Не определена        не измерена
  Научные       Неподтверждённые      Область документа    Полнота
  записи        кандидаты

Только текстовый слой; OCR/графики не обработаны. Полнота не подтверждена.
Интерпретация не запускалась: собраны источники, кандидаты и паспорт разбора.

Кандидаты не подтверждены: 12
У записей статус candidate и контекст unresolved. Они не привязаны к прибору
или условию и не входят в официальную выгрузку. candidates.csv - рабочий черновик,
а не сдача.
```

Почему так: зелёный «Готово» и «проверенные данные» убраны; слово «Нет» в карточке
научных записей прямо говорит, что научных строк нет, а не «всё хорошо».

## Состояние 2: `publications.in_scope=false`

Данные: `interpretation.tables.publications[0].in_scope="false"`,
`exclusion_reason="Моделирование или теория без изготовленных приборов."`,
остальные таблицы пусты.

```
Что получено
  Нет           0                     Вне области         не измерена
  Научные       Неподтверждённые      Область документа    Полнота
  записи        кандидаты

Интерпретация
Черновик модели

[!] Вне области Solar
    Моделирование или теория без изготовленных приборов.

Научные записи отсутствуют
Документ вне области Solar: научные строки по нему не собирались.
Публикации: 1 запись (in_scope=false).
```

Правила:
- `in_scope` показываем словами: `true` -> «В области», `false` -> «Вне области Solar»,
  пусто или незнакомое значение -> «Не указана». Сырые `true`/`false` в интерфейсе
  не оставляем.
- Причина берётся из `exclusion_reason`. Если поле пустое, пишем
  «Причина исключения не указана в извлечённых данных», а не придумываем её.
- Баннер стоит до таблиц, чтобы пустота таблиц не читалась как сбой извлечения.

## Состояние 3: научных строк нет (LLM включена, таблицы пусты)

Данные: `interpretation.status="ok"`, `tables.publications` есть, остальные пять
научных таблиц пусты.

```
Интерпретация
Черновик модели

[ok] Структура и цитаты прошли проверку. Полнота научных данных не подтверждена.

Научные записи отсутствуют
В проверенной интерпретации нет строк научных таблиц: материалы, приборы, слои,
измерения, результаты. Это не значит, что в документе нет данных: полнота
не измерена, часть сведений может быть в прозе или на рисунках.

Публикации: 1 запись
[таблица публикаций]

Материалы
Научных записей нет. Подтверждённых строк для этой таблицы в документе не нашлось.
```

Отдельная карточка таблицы с нулём остаётся: пользователь видит, какая именно
таблица пуста, и не додумывает, что она просто скрыта.

## Состояние 4: неподтверждённые кандидаты

Данные: `result.candidates[]`, у всех `status="candidate"`, `context_status="unresolved"`.
Возможно одновременно с состояниями 1-3.

```
[!] Кандидаты не подтверждены: 12
    У записей статус candidate и контекст unresolved. Они не привязаны к прибору
    или условию и не входят в официальную выгрузку. candidates.csv - рабочий
    черновик, а не сдача.

Файлы результата
[Результат JSON] [Кандидаты CSV] [Отчёт парсера]
```

Если `result.json` недоступен, но `summary.candidates` > 0:

```
[!] Кандидаты не подтверждены: 12
    Сервер сообщает число кандидатов, но result.json не загрузился, поэтому
    статусы записей не проверены. Кандидаты не входят в официальную выгрузку.
```

## Состояние 5: `in_scope` отсутствует или неоднозначен

Данные: `publications[0]` без поля `in_scope`, или `in_scope=""`, или значение вне
`true`/`false`. Раньше такая строка молча считалась «в области»; теперь нет.

```
Что получено
  Нет           3                     Не определена        не измерена
  Научные       Неподтверждённые      Область документа    Полнота
  записи        кандидаты

Интерпретация
Черновик модели

[ok] Структура и цитаты прошли проверку. Полнота научных данных не подтверждена.

Публикации
Публикация   Область       Причина исключения
D001         Не указана    -
```

Если явные значения есть у части публикаций:

```
Что получено
  ...           ...                   Определена не полностью   ...

[!] Область Solar определена не полностью
    Для 1 публикации область в данных не указана, поэтому она не считается
    подтверждённой.
```

Правило: пустое или незнакомое значение никогда не превращается в «в области».
«В области» ставится только когда каждая публикация явно помечена `true`.

| Пустая таблица (научная) | Проверенных записей в этой таблице нет | Научных записей нет. Подтверждённых строк для этой таблицы в документе не нашлось |
| Пустая таблица (публикации, замечания) | Проверенных записей в этой таблице нет | Записей нет |
| Значение `in_scope` в таблице | `true` / `false` / `-` | В области / Вне области Solar / Не указана |

Бейджи стадий (`stages[].status=ok`) не меняются: там `ok` действительно значит
«этап выполнен», и это не обещание полноты.

## Что не делаем

- Не меняем backend, `server.py`, `parse_document.py`, `llm_shell.py`.
- Не считаем `in_scope` по названию файла и не угадываем причину исключения.
- Не пересчитываем покрытие и не показываем выдуманный процент готовности.
- Не скрываем артефакты и не меняем ссылки на них.
- Не убираем таблицы с нулём строк: пустая таблица это факт, а не мусор.

## Семантический слой: отдельное описание статьи

Отдельный блок для области solar и только при `llm != off`. Он показывает
необязательный слой `llm/semantic.json`, который модель добавляет рядом с семью
таблицами. Это описание статьи, а не научные таблицы и не официальная выгрузка.

Источник данных:

| Блок | Поле ответа | Что берём |
| --- | --- | --- |
| Статус слоя | `semantic.json` -> `status` | `ok`, `partial`, `missing`, `rejected` |
| Счётчики | `semantic.json` -> `records`, `errors` | принятые записи по видам и число замечаний |
| Резерв счётчиков | `manifest.solar.semantic_status` / `semantic_counts` | если файл не загрузился |
| Признаки статьи | `study_type`, `data_provenance`, `thematic_relevance`, `scope_reason` | значения и собственные цитаты |
| Записи | `records.layers`, `records.conditions`, `records.metrics` | значения и `field_sources` каждого поля |
| Замечания | `errors[]` | причины отказа и неподтверждённые признаки |

`metadata_evidence[field]` содержит цитату только у подтверждённого признака.
`unknown` приходит без цитаты: это честное «не определено», а не «не подходит».
Отдельного поля `requires_review` в контракте нет, и UI его не выдумывает.

### Каркас

```
[panel: Описание статьи моделью]        <- НОВЫЙ блок, solar + llm != off
  eyebrow: Наблюдения модели
  [semantic_only] [статус слоя] [Не для официальных CSV]
  <lede: что это и чего это не доказывает>

  [Слои N] [Условия N] [Метрики N] [Замечания проверки M]

  <таблица признаков: Признак | Значение | Цитата>
  <таблицы принятых записей: каждое поле со своей цитатой>
  <details: замечания проверки и причины>
  <notice, если файл недоступен или слой отсутствует>
```

Блок стоит после "Параметры разбора / Работа модели" и до "Интерпретация".
Маршрут `#/parse/<id>` не меняется, новой вкладки нет.

### Постоянные подписи

- Бейдж `semantic_only` виден всегда и не зависит от статуса.
- Бейдж `Не для официальных CSV` виден всегда.
- Lede: "Модель отдельно описала тип исследования, происхождение данных и часть
  наблюдений. Эти строки не входят в официальные таблицы и CSV. Буквальная
  цитата подтверждает только то, что значение напечатано в документе; она не
  доказывает научную связь, полноту или правильность вывода."

### Статусы слоя

| `status` | Бейдж | Текст |
| --- | --- | --- |
| `ok` | Собран (нейтральный) | "Для всех показанных значений нашлась буквальная цитата. Это подтверждает только присутствие значения в тексте, а не научную связь или полноту." |
| `partial` | Собран частично (warn) | "Принято N записей, замечаний проверки: M. Ниже только записи с буквальной цитатой; отклонённые и неподтверждённые причины перечислены отдельно." |
| `missing` | Не сформирован (нейтральный) | "Модель не вернула описание статьи. Это не ошибка разбора: официальные таблицы и CSV собираются отдельно. Тип исследования и происхождение данных не определены; пустое значение не означает, что статья не подходит." |
| `rejected` | Отклонён (bad) | "Описание статьи нельзя использовать: <первая ошибка>. Признаки и записи не показываются, чтобы не выдать непроверенное за результат." |
| файл не загрузился | Неизвестно (warn) | "Файл semantic.json недоступен. Статус и счётчики взяты из манифеста; значения и цитаты не показаны, чтобы не выдать неполные данные за полные." |
| старый разбор без слоя | нет бейджа | "Этот разбор создан без семантического слоя: отдельного описания статьи в нём нет." |

`ok` намеренно нейтральный: он значит "ошибок проверки нет", а не "научно
подтверждено". Зелёный "Проверено" здесь запрещён.

### Признаки статьи

| Признак | Значение | Цитата |
| --- | --- | --- |
| Тип исследования | Эксперимент / Расчёт / Смешанное / Обзор / Не определено · требует проверки / Нет данных | "стр. N: «...»" или "Нет подтверждающей цитаты" |
| Происхождение данных | Измерено / Смоделировано / Из литературы / Не определено · требует проверки / Нет данных | то же |
| Тематика | По теме / Частично по теме / Не по теме / Не определено · требует проверки / Нет данных | то же |
| Причина области | формулировка модели | цитата-основание, но не факт |

Правила:
- `null` (слой отсутствует или отклонён) -> "Нет данных", не "unknown".
- `unknown` -> "Не определено · требует проверки", не "не подходит" и не `false`.
- Цитата берётся из `metadata_evidence[field]`. Если её нет, пишем
  "Нет подтверждающей цитаты", а не оставляем пустую ячейку.
- `scope_reason` это пересказ модели. Рядом прямо написано "формулировка модели,
  не буквальный факт": наличие цитаты-основания не превращает вывод в факт.

### Счётчики

```
[Слои 2] [Условия 1] [Метрики 4] [Замечания проверки 1]
```

Первые три - принятые записи по видам. Последний - `errors.length`, и это не
число quarantined-записей: одна запись может дать несколько замечаний, а часть
замечаний относится к признакам статьи, а не к записям. Поэтому подпись
"Замечания проверки", а не "Отклонённые записи".

### Принятые записи и цитаты по полям

Слои: Страница | Название | Роль | Материал | Толщина | Единица толщины
Условия: Страница | Название | Значение | Единица
Метрики: Страница | Название | Значение | Единица

В каждой ячейке значения под самим значением стоит его собственная цитата из
`field_sources[field]`. Одна цитата на строку не показывается как доказательство
всех полей: у каждого непустого поля своя ссылка. Если у поля нет ссылки, ячейка
говорит "Нет подтверждающей цитаты".

Показываем первые 100 записей каждого вида. В заголовке всегда реальное число:
"Показаны первые 100 из N. Полный набор в semantic.json." Если записей меньше,
ограничение не упоминается.

### Замечания проверки

```
<details>
  <summary>Замечания проверки: 3</summary>
  <ul>
    <li>Метрики, запись 3: значение не напечатано в собственной цитате.</li>
    <li>Тип исследования: собственная цитата не подтверждает значение.</li>
  </ul>
</details>
```

Показываем не больше 100 замечаний, но в summary реальное число.

### Чего этот блок не делает

- Не считает `status=ok` научной проверкой и не ставит зелёный "Проверено".
- Не показывает отклонённые записи как значения.
- Не выдаёт `scope_reason` за буквальный факт документа.
- Не смешивает `errors` с числом quarantined-записей.
- Не добавляет semantic в официальные таблицы и CSV.
- Не выдумывает `requires_review`, причину области или цитату.
- Не падает на старом манифесте без блока `solar`: показывает честную пометку.

## Построчный черновик (draft.json)

Отдельный диагностический вид ответа модели. Он появляется, когда строгая
интерпретация отклонена целиком, но модель всё же вернула строки: черновик
сохраняет каждую строку со статусом и причиной отказа.

Источник данных - только манифест: `manifest.solar.draft_status` и
`manifest.solar.draft_counts` (`rows`, `accepted`, `quarantined`). Сами строки
лежат в артефакте `llm/draft.json`, ссылка на него уже есть в блоке файлов.
Второй renderer таблиц не нужен: пользователь видит счётчики и где лежит файл.

| `draft_status` | Что показываем |
| --- | --- |
| `partial` / `ok` с `accepted > 0` | счётчики принятых и отклонённых строк и ссылку на `draft.json` |
| `partial` / `ok` с `accepted = 0` | ничего дополнительно: принятых строк нет |
| `missing` / `blocked` / `error` | ничего дополнительно: черновика нет |

### Отклонённая интерпретация

```
[!] Строгая интерпретация отклонена
    Построчный черновик сохранил 3 принятых и 2 отклонённых строк. Не официальные CSV.
    Это диагностический черновик с причинами отказа, а не подтверждённые научные
    записи. Независимые строки сохранены в draft.json.
    [Построчный черновик с причинами отказа · draft.json]

[!] Интерпретация не прошла проверку
    <причина отклонения>
```

Правила:
- Нельзя писать «научных данных нет», если черновик сохранил принятые строки:
  иначе пользователь решит, что модель ничего не вернула.
- Принятая строка черновика не называется подтверждённым научным результатом
  и не попадает в официальные CSV.
- В карточке «Что получено» подпись становится «Научные записи (строгие)», а под
  сеткой стоит пояснение, что принятые строки черновика лежат в `draft.json`.
- Подписи артефактов: `response.json` - «Исходный ответ модели»,
  `draft.json` - «Построчный черновик с причинами отказа».

## Привязка условий и научная полнота

Строгий `interpretation.status = ok` значит, что прошли формальные проверки
структуры и буквальности цитат. Это не проверка научных связей и не проверка
полноты. Поэтому зелёный бейдж «Проверка пройдена» убран.

### Источник данных

| Поле | Где | Что берём |
| --- | --- | --- |
| Привязка | `interpretation.attribution` | `state`, `requires_review`, `counts`, `rows`, `truncated` |
| Резерв | `manifest.solar.attribution_state`, `attribution_counts`, `requires_review` | если файл интерпретации не загрузился |
| Явные флаги | `manifest.solar.scientific_binding_verification`, `scientific_completeness_verification` | оба `not_verified` |

`attribution` - это инвентарь чувствительных полей (условия процесса и размер
выборки), а не вердикт. `rows` содержит `{table, key, fields}` и не содержит
значений ячеек.

### Итог строгой интерпретации

```
[Формальные проверки пройдены]   (нейтральный бейдж, не зелёный)
Структура и цитаты прошли формальную проверку. Научные связи и полнота
автоматически не подтверждены.
```

Фраза «Научные связи и полнота автоматически не подтверждены» показывается
всегда при `status = ok`, даже когда инвентарь пуст.

### Инвентарь привязки

`requires_review` в контракте всегда `true`: научные связи не подтверждены
глобально, даже когда инвентарь пуст. Поэтому показ предупреждения решает не
`requires_review`, а наличие чувствительных полей: `counts.fields > 0` или
`counts.rows > 0`.

| Состояние | Что показываем |
| --- | --- |
| `state = unverified` и `counts.fields > 0` | компактный список полей с числом строк и предупреждение о ручной проверке привязки |
| `state = none` | «Чувствительных полей привязки не найдено. Это только пустой инвентарь: научные связи и полнота не подтверждены.» |
| `unverified`, но `counts.fields = 0` и `counts.rows = 0` | то же пустое состояние: предупреждения о несуществующих полях нет |
| атрибуции нет, есть `manifest.solar.attribution_state` | состояние и счётчики из манифеста, без списка полей |
| нет ни файла, ни манифеста (старый разбор) | «Сведения о привязке отсутствуют: научные связи не подтверждены.» |

Пример списка (не больше 12 полей, реальные числа):

```
[!] Требуют проверки привязки: 14 строк, 18 полей
    Температура отжига - 6 строк
    Атмосфера - 5 строк
    Число приборов - 3 строки
    Показаны первые 3 из 7 полей. Полный инвентарь в interpretation.json.
```

Правила:
- Пустой инвентарь (`state = none`) не означает «вся наука проверена» и не
  означает «проверка не нужна»: это только отсутствие чувствительных полей в
  этом наборе.
- `requires_review = true` при пустом инвентаре не превращается в предупреждение
  о несуществующих полях.
- Инвентарь не называется карантином и не меняет данные: ни одна строка не
  отклонена из-за него.
- Поля подписаны по-русски, неизвестное имя показывается как есть.
- Старый разбор без метаданных даёт «неизвестно», а не «подтверждено».
- Блок semantic-таблиц не меняется: привязка это отдельное предупреждение.
