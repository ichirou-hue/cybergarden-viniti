# План команды: обе области, RAG первым

## Что согласовано

Один продукт для двух областей: извлечение проверяемых научных результатов из PDF. Общая платформа и два тематических обработчика. RAG первым проходит весь путь от реальной статьи до экспорта; solar разрабатывается параллельно.

Ресурсы: ноутбуки, большой доступ к бесплатным моделям по API, ограниченный доступ к дорогим моделям, подписки Codex Plus. Конкретные API, их лимиты, условия обработки документов и качество ещё не проверены. Подписка на инструмент разработки не означает наличие API-квоты для приложения.

Это организационный план, не согласованный технический дизайн API. Продакшен-код в рамках исследования не менялся.

## Задача простыми словами

Превратить статьи в связанные записи: объект → условия → показатель → исходное/нормализованное значение → точное место в PDF → замечания проверки.

RAG — предмет статей, а не требование создать чат-бота. Solar — экспериментальные однопереходные тонкоплёночные приборы, не тандемы и не чисто расчётные работы.

## Рабочее распределение

Назначения ниже — рабочее распределение по согласованию пользователя.

| Участник | Ответственность | Проверяемый результат |
|---|---|---|
| Илья Б — frontend | Каталог публикаций и результатов, переключение области, предметные фильтры, состояние обработки | Пользователь находит нужные записи и понимает, что обработано, а что завершилось ошибкой |
| Егор В — frontend | Просмотр PDF/источников, исходные и нормализованные значения, связанные сущности и замечания | Из результата можно перейти к доказательству на странице и понять причину предупреждения |
| Митя — backend | Общий контракт, загрузка и пакетная обработка, хранение, статусы, API, CSV-экспорт, интеграция обработчиков | Оба направления проходят одинаковый путь обработки и выгружаются отдельными совместимыми наборами |
| Илья С — ML | RAG: конфигурации, датасеты, задачи, эксперименты, метрики, нормализация и проверки | Связанные результаты на реальных dev-статьях с измерением качества |
| Даниил — ML | Solar: материалы, приборы, слои, измерения, показатели, нормализация и физические проверки | Связанные результаты на реальных dev-статьях с измерением качества |

OCR и разбор таблиц — общая работа ML-разработчиков с Митей. Backend не должен становиться единственным владельцем предметных правил. Каждый ML-разработчик отдаёт свой обработчик вместе с проверками и примерами результата.

## Первые 2–4 часа

1. Митя и оба ML-разработчика фиксируют общий формат результата обработчика: область, публикация, сущности, результаты, источники, замечания и ошибки. Предметные поля остаются разными.
2. Илья С и Даниил выбирают по несколько разнообразных dev-статей: текстовые результаты, таблицы, несколько вариантов объекта; для RAG обязательно включить скан.
3. Проверяют доступные API: качество, структурированный ответ, задержка, лимиты, стоимость и разрешённость передачи PDF.
4. Frontend-разработчики согласуют разделение компонентов и структуру ответа с backend. Для нового крупного UI сначала подготовить варианты и получить выбор пользователя.
5. Не переписывают стек и не создают два приложения.

## Этапы и контрольные точки

Время ниже — ориентир от начала согласованной работы. Нужно пересчитать по фактически оставшемуся времени, включая сон и перерывы.

### До 12–16 часов

- RAG: реальная статья → связанные сущности → результаты → подтверждение в PDF → замечания → экспорт.
- Solar: небольшой рабочий набор dev-примеров с тем же общим контрактом.
- CSV-экспорт начинается на этом этапе, а не перед сдачей.
- Измеряется длительность обработки страницы/статьи, чтобы оценить время прогона test.

Если solar не выдаёт достоверных связанных записей, объявить его экспериментальным и защитить основной результат RAG. Не маскировать пропуски выдуманными значениями.

### До 30–34 часов

- Улучшать ошибки на dev, расширять покрытие таблиц и сканов.
- Проверять не только числа, но и правильность связи с объектом, условиями и заголовками.
- Запускать пакетную обработку test заблаговременно, с журналом ошибок и возможностью продолжения.
- Имена D001/P001 повторяются между областями: хранить область вместе с идентификатором.

### Последние 10–14 часов

- Заморозить новые крупные функции.
- Прогнать проверки экспорта, связей и источников, smoke-тесты и реальную демонстрацию.
- Подготовить паспорт данных, результаты измерения качества, ограничения и причины замечаний.
- Иметь сохранённый результат обработки и воспроизводимый сценарий, не зависящий целиком от доступности API в момент защиты.

## Стратегия использования моделей

- Сначала использовать текстовый слой и координаты PDF, а не отправлять каждую страницу как изображение.
- Бесплатную модель применять только после короткого сравнения с dev_gold. Доступность не гарантирует точность, скорость или стабильный лимит.
- Дорогую модель/VLM резервировать для сложных таблиц, сканов и неоднозначных связей, а также контрольной выборки.
- Кэшировать результаты по документу/странице и версии обработки; повторные попытки ограничивать.
- Требовать структурированный результат, затем проверять типы, ссылки и наличие источника программно.
- Ответ модели — кандидат на извлечение, не доказательство: цитату и число нужно сверять со страницей.
- Не обучать большую модель с нуля. Не добавлять чат как отвлечение от критериев кейса.
- Codex использовать для разработки и тестов; доступ приложения к API настраивать и проверять отдельно.

## Критерии готовности

- Для каждой области есть отдельный набор связанных данных по заявленному охвату.
- У извлечённого результата есть проверяемый источник; неизвестные значения не выдуманы.
- Сохраняются исходная и нормализованная записи; замечания не уничтожают исходные результаты.
- Интерфейс позволяет найти результат, увидеть связанные условия и открыть источник.
- Экспорт проверен инструментом соответствующего комплекта. Его техническое прохождение не выдаётся за метрику научной точности.
- Качество измерено на dev отдельно по статьям и основным сущностям/полям, с описанной методикой.
- Известные ограничения и необработанные статьи перечислены честно.
