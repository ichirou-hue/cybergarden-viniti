# Утверждённый процесс обработки документов

Статус: согласован пользователем 2026-11-21. Это целевой процесс; наличие документа не означает, что все стадии уже реализованы или проверены на корпусе.

## Последовательность

1. **Вход:** пользователь загружает PDF и выбирает готовый либо пользовательский профиль извлечения.
2. **Разбор документа:** парсер извлекает текст и таблицы, OCR распознаёт сканы; сохраняются страницы, координаты и изображения.
3. **Изображения и графики:** vision-модель должна извлекать доступные чтения. Это не обещание полного оцифровывания графиков.
4. **Интерпретация:** LLM выделяет сущности, значения и связи в соответствии с профилем.
5. **Черновой паспорт:** код формирует JSON, проверяет технические типы и ссылки, выполняет обоснованные пересчёты единиц. Сохраняются исходные значения и источники.
6. **Аудит:** отдельный LLM рассматривает паспорт вместе с источником, не переписывая ни паспорт, ни PDF, и возвращает замечания.
7. **Экспорт:** код формирует CSV-таблицы из паспорта по соответствующему фиксированному адаптеру и `submission_template`: solar и RAG имеют разные шаблоны.

На сайте должны быть доступны результаты, источники и замечания. Наличие замечаний не является причиной скрывать или удалять исходные данные. Некорректная техническая структура блокирует готовый экспорт до устранения ошибки.

## Профиль

Пользователь задаёт сущности, поля, их семантику, типы, связи, единицы/пересчёты и обязательность.

Пользовательского пункта **«правила проверки» нет**. Технические проверки — внутренняя ответственность программы.

## Первый эксперимент проверки

Начинаем с универсального LLM-аудита **без перечисления предметных проверок**. Его результат сравниваем с dev-разметкой и источниками: полезные замечания, пропуски, необоснованные замечания. Эталон сам по себе не доказывает ложность нового замечания: спорные случаи проверяются по статье.

Существующие детерминированные solar-проверки должны быть отделены от этого эксперимента и не выдаваться за находки универсального LLM-аудита. Предметные инструкции можно добавить позднее и сравнить результаты двух подходов.

Отсутствие замечаний означает только «проверяющая модель не выявила проблем», а не гарантированную достоверность. Соответствие кейсу требует проверить фактическое покрытие требуемых организаторами сценариев.

## Отчёт проверки

Каждое замечание содержит:

- связанные записи и поля паспорта;
- объяснение несогласованности;
- ссылки на подтверждающие места документа;
- предполагаемый тип проблемы: извлечение, противоречие источника или недостаток сведений;
- статус, не выдающий подозрение модели за доказанную ошибку.

CSV заполняет программа по JSON; LLM не конструирует CSV и не додумывает пропуски ради заполнения шаблона.

## Что есть сейчас и что утверждено на будущее

| Область | Проверенный статус |
|---|---|
| PDF и OCR | PDF-разбор и Docling/OCR реализованы отдельными компонентами; см. [гайд profile extraction core](../2026-11-20-profile-core-guide.md) и [гайд Docling](../2026-11-20-docling-adapter-guide.md). |
| Профили, извлечение, экспорт | Есть CLI profile extraction core и solar-адаптер. Solar CSV создаются по своему шаблону; это не означает готовность общего веб-процесса. |
| Чтение графиков | Docling сохраняет crops; его optional native chart2csv настроен, но живой chart-инференс не проверен. OpenRouter vision — незавершённый, не подключённый локальный прототип, не включённый в публикуемый проверенный срез. |
| LLM-аудит паспорта | Универсальный отдельный аудит ещё не реализован. Согласован первый эксперимент без предметных чек-листов; результат сравнивается с dev-gold и источниками. |
| UI и серверный процесс | Новой UI/backend-интеграции нет; этот документ не вводит существующие endpoints. |

Целевой пользовательский профиль задаёт сущности, поля и их семантику, типы, связи, единицы и пересчёты, обязательность, без пункта «проверочные правила». В текущем техническом JSON-формате CLI ещё поддерживаются необязательные числовые ограничения `minimum`/`maximum`; это не означает, что пользователь обязан их задавать или что согласованный UI уже реализован. Технические проверки типов, ссылок и расчётов остаются в коде. Подробности следующего UX-этапа — в [дорожной карте профилей](2026-11-21-profile-ux-roadmap.md).
