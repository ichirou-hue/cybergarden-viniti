# ADR-0002: Минимальное ядро извлечения и декларативные профили

- Статус: Принят
- Дата: 2026-11-20

## Контекст

Даниил утвердил engine + declarative profiles: в его ML-контуре сначала solar, затем RAG. Это уточняет локальный порядок разработки, а не перераспределяет командную ответственность из `docs/requirements/`. Заменяем ADR-0001; изоляция от сайта, сохранение источников и атомарность экспорта остаются.

**Есть:** `extraction_core.py` реализует ограниченный compiler профилей, generic field validation, script-candidates, маршруты `scripts/auto/model` и export envelope; `extract_document.py` — CLI. `profiles/solar.json` направляет в фиксированный `solar_csv` адаптер; `profiles/custom-example.json` демонстрирует generic поля. `solar_schema.py` задаёт семь таблиц, словари и единицы; `solar_facts.py` выполняет source validation, нормализацию, предметные проверки и CSV export; `solar_extract.py` содержит solar prompt и OpenRouter-клиент. Generic-поля поддерживают типы `text/number/boolean/id/reference`, ссылки, единицы и min/max. `evaluate_extraction.py` реализует offline mention-level сравнение CSV с basic/context и micro/macro отчётами. Solar evidence остаётся на уровне записи; generic-профиль требует field-level цитату. Для API используется `response_format: json_object`; compiler response shape и локальная валидация не означают provider-enforced JSON Schema. Реализация не подтверждает полноту или научную точность; live-вызов не проверен.

**Ограничения и дальнейшая работа:** это минимальное ядро, не framework; OCR, chunking, universal all-fields discovery и интеграция в сайт не реализованы. Контракт передачи результата **provisional до согласования с Митей**; `server.py`, `library.py`, `static` не менялись в рамках этой реализации. UI и его прототипирование вне этой задачи.

## Варианты

### A. Оставить solar-only pipeline

Минимальная стоимость, знакомые тесты, нет миграционных рисков. Но новая область дублирует orchestration и проверки, пользовательские схемы не поддерживаются; существующая обязательная модель не даёт offline extraction.

### B. Тонкое общее ядро + профили + предметные адаптеры — выбран

Небольшая стоимость выделения функций, подменяемый клиент и чистые стадии удобны для тестов; переход обратим через сохранение solar CLI/адаптера. Scripts быстры и бесплатны, LLM добавляет задержку и стоимость. Главный риск — ложная уверенность в полноте эвристик; устраняем явным coverage и модельным проходом.

### C. Универсальный workflow framework

Плагины, DSL правил, очереди и динамические DAG дают гибкость, но существенно увеличивают сложность, стоимость, поверхность ошибок и объём тестирования без выигрыша текущему solar-срезу. Откладываем.

## Решение

### Минимальные интерфейсы (план, не существующий API)

| Интерфейс | Ответственность |
|---|---|
| `compile_profile(profile) -> compiled` | Проверить декларацию и построить JSON Schema ответа модели, описание полей для prompt и план стадий из одного источника. |
| `run(document, compiled, *, mode, model_client=None) -> result` | Последовательно выполнить script/model стадии, затем общую и предметную валидацию; сеть только через внедрённый клиент. |
| `export_solar(result, output_dir)` | Отобразить валидные сущности в **ровно семь CSV** по `solar_schema.TABLES`, без новых колонок; diagnostic JSON — sidecar. |
| `evaluate_csv(pred_dir, gold_dir, matching_spec) -> report` | Независимо читать CSV, сопоставлять содержание и связи, считать качество без равенства внутренних ID. |

Профиль — обычный JSON-совместимый словарь: `id`, `version`, `entities` (поля, типы, обязательность, enum, ссылки), `metrics` (aliases, допустимые явные единицы и коэффициенты), `stages` (целевые поля и маршрут `script/model/auto`), имена предметных проверок. Compiler отклоняет неизвестные типы/ссылки/правила. Никаких произвольных Python-выражений, импортов из профиля, языка правил или плагинной системы: небольшой фиксированный registry функций. Solar physics и mapping CSV остаются предметными, не растворяются в generic engine.

### Маршрутизация и предел эвристик

1. Script-first означает локальное чтение PDF, поиск кандидатов и детерминированные проверки, **не** остановку после regex match. Generic numeric keyword extraction выдаёт только кандидаты `(field/metric, raw, unit?, evidence)`. Оно не создаёт выдуманные device/measurement, scope, primary/cited, aggregation или связи.
2. `--mode auto`: сначала scripts, затем OpenRouter для неразрешённых полей/контекста. Для solar высокой полноты нужен LLM-проход по доступному документу, а не только найденным snippets: отсутствие match не доказывает отсутствие данных. Даже несколько успешных matches не отменяют этот проход. Полнота подтверждается eval, не самим фактом вызова LLM.
3. `--mode scripts`: полностью offline, без ключа и сетевых вызовов; сохраняет кандидатов и явное `coverage=partial`, причины и непроверенные поля/страницы. Не обещает полный solar CSV. Отсутствующие связи остаются неизвестными, а не заполняются ради checker. Ошибка API в auto не маскируется успешным offline-результатом.
4. `--mode model`: извлечение всех полей профиля моделью с последующей локальной проверкой. Для произвольного document-schema extraction это основной путь; custom profile необязателен (без него используется выбранный встроенный профиль). Compiler поддерживает ограниченную декларацию, не обещает произвольную JSON Schema. Scripts могут помогать, но не исключают из запроса ненумерические поля.
5. Нет текста, превышен бюджет или неподдерживаемые страницы — явная ошибка/частичный охват, не молчаливая обрезка. OCR/chunking не добавляем этим решением. API сохраняет ограничения размера, повторов и защиту ключа; документы отправляются только при разрешённости такой передачи.

### Общий JSON и доказательства

Envelope: `schema_version`, `profile_id`, `profile_version`, `document` (`publication_id`, `sha256`), `records`, `candidates`, `sources`, `issues`, `coverage`, `run` (mode/model/revision). Внутренние неизвестные значения — `null`, пустая строка появляется только в CSV-адаптере.

Каждая запись имеет `id`, `entity`, `fields`; каждое поле — `raw`, `value`, `unit`, `status`, `evidence_refs`. Статусы извлечения: `extracted`, `unknown`, `present_not_extractable`, `absent`. Последний требует явного подтверждения отсутствия в указанной области, не «не нашлось»; `present_not_extractable` требует подтверждения присутствия. Кандидат без разрешённого контекста остаётся в `candidates`, не становится готовой записью.

Evidence указывает source ID, поле и роль (`value/unit/context`), локальные page/quote/bbox и `verification=literal_verified|unverified|rejected`; bbox не выдумывает модель. `literal_verified` доказывает соответствие тексту, не научную правильность связи. Источники обязательны для всех содержательных утверждений, включая title, scope, единицы, условия и связи; технические ID и вычисленные поля вместо цитаты имеют provenance на исходные поля и правило. Неизвестные и отклонённые утверждения не экспортируются как установленные факты.

Общие проверки: схема, ID/FK, полные числовые токены со знаками, field-level evidence, явные единицы, конечные числа, сохранение raw при нормализации, корректность duplicate. Предметные: solar scope, сопоставимость, физические правила. Неприменимая проверка даёт `not_checked` с причиной; противоречие не исправляет исходные данные. Не переносить известные дефекты ревью в общее ядро.

Solar adapter сохраняет точные заголовки, порядок, enum и пустые значения текущего шаблона, пишет комплект атомарно в новый каталог. `unknown` не переводится в `absent`. Неустранимые обязательные связи/scope блокируют готовый комплект, оставляя диагностический JSON; допустимый частичный экспорт явно помечается в sidecar и issues.

### Оценка и итерации

Evaluator не вызывает extractor и не использует gold при извлечении. В пределах публикации сопоставляет сущности по нормализованным содержательным атрибутам и разрешённым связям, затем результаты по метрике, контексту устройства/измерения, aggregation, происхождению и времени. ID используются только для разыменования внутри своего комплекта; произвольное переименование ID не меняет оценку.

Matching — детерминированное взаимно-однозначное, с фиксированными допусками и явным отчётом неоднозначности; одинаковое число само по себе не критерий совпадения. Не подбирать пары по оцениваемому значению, чтобы скрыть ошибки значения. Считать precision/recall записей, accuracy полей/значений после matching, ошибки связей, micro и macro по статьям; пропуски/сбои входят в recall. CSV checker отдельно проверяет формат, evidence — отдельная проверка источников, не показатель полноты.

Цикл: фиксированный dev-прогон → сравнение с dev_gold → классификация ошибок → изменение профиля/prompt/проверки → повтор на той же выборке и регрессиях. Сохранять версии, mode/model, coverage, время и стоимость; подбор на dev не называть независимой test-оценкой.

## Последствия

Общие механизмы переиспользуются без изменения сайта; solar-семантика остаётся явной. Цена — версия нового JSON и модельный бюджет; декларация сама по себе не решает семантическое связывание и не гарантирует качество.

План developer:

1. Закрыть ревью и QA-регрессии текущего solar-среза до выделения общего кода.
2. Ввести минимальный profile/compiler и field-level result; сохранить solar CLI через адаптер, добавить тесты неизвестных полей, единиц и источников.
3. Ввести scripts/auto/model и тесты «ноль matches ≠ absent», «scripts никогда не вызывает сеть», «найденное число не создаёт устройство».
4. Подключить exact-seven-CSV adapter и evaluator; проверить инвариант к переименованию ID и неоднозначные matching-сценарии.
5. Измерить solar на dev/dev_gold и провести итерации; только затем добавить RAG-профиль. Контракт передачи результата согласовать с Митей отдельно; UI не разрабатывать.
