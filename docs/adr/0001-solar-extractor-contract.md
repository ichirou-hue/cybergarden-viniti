# ADR-0001: Изолированный solar extractor с предварительным контрактом

- Статус: Заменён ADR-0002
- Дата: 2026-11-20

## Контекст

Первый вертикальный срез части Даниила: текстовый PDF → OpenRouter → проверяемые solar-записи → нормализация/семантические проверки → семь CSV. Это экспериментальный обработчик, не полноценное корпусное решение. Контракт с Митей **не согласован**; описанный ниже формат **provisional**, не общий API.

Изучены `pdf_source.py`, `rag_facts.py`, `analyze_pdfs.py`, `library.py`, оба документа `docs/requirements/`. Существующих ADR не обнаружено. Сейчас `library.analyze_pdf` напрямую вызывает RAG, SQLite/UI ожидают `facts`; существующий CLI пишет JSONL, допускает частичный успех. `pdf_source.extract(bytes)` уже возвращает страницы, цитаты, bbox и локальные source ID, строки/ячейки таблиц, предупреждения; лимит — 150 страниц. `library` ограничивает вход 20 МиБ. Из `rag_facts` полезен подход сохранения raw/evidence/issues, но не предметные правила и не нормализация процентов в доли.

Прямое чтение ZIP в этой сессии не удалось: запуск Python через shell запрещён разрешениями, `read` не читает ZIP. Сведения о solar-шаблоне ниже основаны на проверенном ранее разборе требований, **точные CSV-заголовки здесь не утверждаются**. Перед реализацией экспорта developer обязан прочитать README и заголовки из `docs/materials/solar-participant-kit.zip` через `zipfile`; не восстанавливать схему по этому ADR.

## Варианты

### A. Оставить как есть

Нулевая стоимость и риск регрессии, быстрые локальные эвристики легко тестировать. Solar, связи сущностей и CSV отсутствуют — задачу не закрывает.

### B. Небольшой независимый пакет `solar/` и CLI — выбран

Повторное использование PDF evidence, без новых зависимостей и изменений server/UI/storage. Чистые нормализация, проверка и экспорт тестируются без API; решение легко заменить адаптером после согласования. Цена — временный отдельный контракт, API-задержки и стоимость вызовов, последующее согласование с backend.

### C. Сразу общий многопредметный pipeline с очередью, OCR и новым API

Удобнее для будущего корпуса, но дорого, рискованно для существующего RAG, требует несогласованных изменений Мити; хуже обратимость и срок первого результата. Сейчас избыточно.

## Решение

### Что реализовано в текущем vertical slice (не исходное предложение)

Реализация находится в корневых модулях `solar_schema.py`, `solar_facts.py` и `solar_extract.py`, а не в предложенном пакете `solar/`. Текущий envelope использует `schema_version="solar-1"` и поля `track`, `publication_id`, `sha256`, `pages`, `sources`, `tables`, `evidence`, `warnings`, `extraction`; функции-среза: `prepare_pdf`, `messages`, `complete`, `finalize`, `analyze_pdf`. Это provisional контракт, он не является согласованным API Мити.

Реальные пределы включают 40 МиБ на PDF, ограничение 150 страниц у используемого PDF extractor и бюджет запроса по умолчанию 200000 символов без обрезания/chunking. Source IDs текущего PDF — целые числа. CSV-поля принимаются как строки; отсутствующие значения сериализуются пустой строкой, не JSON null. CLI обрабатывает один PDF за запуск, а `--prepare` формирует запрос без сетевого вызова.

Текущая проверка evidence ограничена проверкой существования source ID, страницы и буквального вхождения цитаты/числа в текст источника. Поле `evidence` индексирует использованные источники на уровне записи; оно не реализует предложенную проверку доказательств по каждому полю. Field-level semantic/header verification, общий deadline и jitter, OCR и cell accuracy не следует считать реализованными гарантиями. Повторы ограничены параметром retries и фиксированной экспоненциальной задержкой с потолком; это не deadline/jitter-механизм.

Остальной текст ниже фиксирует исходное предложение архитектора, а не спецификацию уже реализованного поведения; перечисленные там будущие гарантии не подразумеваются текущим срезом.

### Границы и последовательность

Предлагаемые файлы (не отдельные сервисы):

- `solar/__init__.py`: `extract_pdf(data: bytes, publication_id: str, *, client) -> dict`; orchestration, локальные лимиты, версия и SHA-256.
- `solar/openrouter.py`: транспорт `urllib`, prompt и JSON-schema кандидатов; клиент подменяется в тестах.
- `solar/validation.py`: проверка evidence/ссылок, нормализация и семантические правила; без сети.
- `solar/export.py`: адаптер к точным семи solar CSV.
- `solar/__main__.py`: `python -m solar input.pdf --output-dir NEW_DIR`; первый срез — один PDF за запуск, без базы, HTTP и batch resume.

Импортировать только `pdf_source.extract`, не `library.analyze_pdf` и не RAG-анализатор. Общие файлы не менять. Сначала ограничить размер 20 МиБ и страницы существующими 150, возвращать явную ошибку лимита; это исключает часть корпуса, включая P042. Пересмотр лимитов — отдельное измеренное решение.

### Доверие к модели и источникам

1. Извлечь PDF локально. Нет текстовых sources → ошибка `no_text_layer`, ненулевой exit, API не вызывается. OCR отсутствует; текстовый слой сам по себе также не доказывает точность распознавания.
2. В первый срез передавать весь доступный набор sources одного PDF с ID, страницами, строками и ячейками таблиц. Ограничить размер запроса; при превышении — `context_limit`, **не обрезать молча**. Chunking и объединение сущностей отложить.
3. Модель получает текст как недоверенные данные, не инструкции. Возвращает кандидаты сущностей/полей, raw-значения, provenance, ссылки на source ID и индексы ячеек. Нужны источники также для units, заголовков, устройства, условий, scope и происхождения; одной ссылки на число недостаточно.
4. Программно проверить существование каждого ID в sources именно данного PDF, индексы ячеек, страницу и наличие raw-значения/цитаты. Допустима только явно описанная нормализация пробелов/Unicode, не fuzzy-поиск числа по всему документу. Проверить связь ячейки с заголовком и контекстом; при неоднозначности — issue, не утверждение.
5. Итоговые `page`, `bbox`, `quote` брать **из локального PDF**, не из ответа модели. Bbox — `[x0, top, x1, bottom]` в PDF points, начало сверху слева, страницы с 1. Дополнительная проверка конечности, порядка координат и попадания в границы страницы через `pdfplumber`. Не выдавать bbox всей строки за точный bbox числа.
6. `verified` означает проверенное текстовое соответствие, **не научную достоверность и не доказанную семантическую связь**. Выдуманные источники/неподтверждённые утверждения остаются в диагностике, не становятся extracted-значениями. Физическое противоречие у подтверждённой записи сохраняется вместе с исходной записью.

Пустые/нетекстовые страницы при наличии остальных sources → `coverage=partial`, номера пропущенных страниц и предупреждение `ocr_unsupported_or_empty_page`; не называть их достоверно сканами. Графики без текстовых чисел не оцифровывать. Не использовать `absent` для непройденных страниц/полей; `present_not_extractable` — только если присутствие сведений действительно установлено.

### Минимальный JSON-контракт (provisional)

Внешняя оболочка: `schema_version="solar-provisional-0.1"`, `track`, `publication_id`, `document_sha256`, `coverage` (`text_only`/`partial`), `warnings`, `scope`, `tables`, `evidence`. `tables` содержит семь массивов с именами CSV; имена полей строк совпадают с проверенным шаблоном. Неизвестное в JSON — `null`, в CSV — пустая строка, не `0`, `NaN` или `"unknown"`. Все поля строки определяет шаблон, а не LLM. ID уникальны внутри публикации; ссылки проверяются по `(publication_id, id)`.

`scope.decision`: `include`/`exclude`/`undetermined`; reason и evidence обязательны для определённого решения. Включать экспериментальные изготовленные однопереходные тонкоплёночные устройства; тандемы/расчёт без образца исключать. В смешанной статье фильтровать устройства, не выкидывать автоматически всю статью. Неопределённость не превращать в include.

`evidence` — локальный sidecar: таблица, ID записи, список подтверждаемых полей, source ID, необязательный индекс ячейки с 0, проверенные page/bbox/quote, статус. CSV получает поля источника по своему шаблону, не дополнительные колонки bbox. Ссылок может быть несколько на одну запись.

Ниже **сокращённый синтетический пример**, не данные корпуса и не полный перечень CSV-полей. SHA-256 показан условно. Evidence численного результата не подтверждает автоматически scope, primary или связи с прибором:

```json
{
  "schema_version": "solar-provisional-0.1",
  "track": "solar",
  "publication_id": "example",
  "document_sha256": "<sha256-of-input-bytes>",
  "coverage": "text_only",
  "warnings": ["scope_and_context_require_review"],
  "scope": {"decision": "undetermined", "reason": "Недостаточно контекста", "source_ids": []},
  "tables": {
    "publications": [{"publication_id": "example", "title": null}],
    "materials": [],
    "devices": [],
    "layers": [],
    "measurements": [],
    "results": [{
      "publication_id": "example", "result_id": "r1",
      "device_id": null, "measurement_id": null, "material_id": null,
      "metric_name": "PCE", "raw_value": "20", "raw_unit": "%",
      "normalized_value": 20, "normalized_unit": "%",
      "result_origin": null, "cited_publication_id": null,
      "source_page": 1, "source_fragment": "PCE = 20%",
      "extraction_status": "extracted"
    }],
    "issues": []
  },
  "evidence": [{
    "table": "results", "record_id": "r1",
    "fields": ["metric_name", "raw_value", "raw_unit"],
    "source_id": 7, "page": 1,
    "bbox": [40, 100, 160, 112], "quote": "PCE = 20%",
    "verification": "verified"
  }]

```

Этот пример допускается как диагностический JSON, но **не готов к CSV-публикации**: недостающие обязательные связи/scope должны дать структурированные issues по точному шаблону. Нельзя сочинять прибор/измерение ради прохождения checker. До согласования с Митей JSON — артефакт CLI, не контракт сервера.

### Нормализация и semantic validator

- Разделять `primary` и `cited` по подтверждённому контексту; неизвестное оставить пустым с issue, не считать primary по умолчанию. Forward/reverse, champion/mean, разные условия и устройства не объединять. Дубликат — отдельное упоминание с `duplicate_of`; различающиеся значения — не дубликаты.
- Числа разбирать через `Decimal`, запретить bool, NaN, ±Infinity, переполнение при выводе; JSON с `allow_nan=False`. Диапазоны и `±` не сводить молча к одному числу. Сохранять raw.
- Только явные единицы: PCE/FF → %, Voc → V, Jsc → mA/cm², Eg → eV, толщина → nm, площадь → cm², время → h. Доли переводить в проценты лишь при явной шкале, 0.8 без единицы не трактовать автоматически. Неизвестная единица → normalized null + issue.
- Проверять ID/FK, перечисления, типы, источники и сопоставимость. PCE: `100 * Voc[V] * Jsc[mA/cm²] * (FF[%]/100) / Pin[mW/cm²]`; относительное расхождение >3% отмечать только при известном ненулевом Pin и одинаковом эксперименте, без предположения «1 sun = условия по умолчанию». При нулевой опорной PCE относительная проверка неприменима.
- Voc < Eg/q, Jsc_EQE против Jsc (>5%, относительно Jsc ВАХ), champion против среднего — только при подтверждённой сопоставимости; иначе `not_checked` с причиной в диагностике. PCE/FF вне [0,100]% — issue. Не изобретать более узкие физические пороги Jsc из отсутствующей спецификации.

### API, ошибки и экспорт

`OPENROUTER_API_KEY`, `OPENROUTER_MODEL` обязательны; конечные положительные timeout/output-token/request-size limits — конфигурация окружения с проверкой. HTTPS OpenRouter, без передачи ключа произвольному endpoint. Использовать structured `json_schema` для выбранной поддерживающей модели, затем локальную проверку типов/полей/ссылок: schema не доказывает истинность. Неподдерживаемый режим, отказ модели, усечённый/невалидный JSON — явная ошибка, без тихого fallback в свободный текст.

Не более трёх попыток всего; timeout, 429 и временные 5xx — bounded backoff/jitter, ограниченный Retry-After и общий deadline. 400/401/403, неправильная схема и context limit не повторять. Ограничить также размер ответа. Логи: код ошибки/попытка/длительность, без Authorization, ключей, полного prompt и response body. Перед сетевым прогоном подтвердить разрешённость передачи текстов провайдеру.

Ошибки чтения/API/схемы/полное отсутствие текста → ненулевой exit, **CSV не публикуются**. Неопределённый scope и незакрытые обязательные связи также блокируют готовый CSV, оставляя диагностический JSON. Физические предупреждения не удаляют подтверждённые данные. Partial coverage явно отражается в JSON и issues; CLI возвращает отдельный ненулевой код предупреждения, даже если комплект записан.

Атомарность — на уровне **комплекта**, не отдельных файлов: сначала JSON + все семь CSV (включая пустые с заголовками) в соседнюю staging-директорию той же файловой системы; проверить весь комплект, закрыть файлы, затем rename в новую отсутствующую output-директорию. При ошибке staging убрать, старый результат не трогать. Существующий output отклонять, не заменять семь CSV по одному. UTF-8, comma, decimal dot; точный порядок заголовков из ZIP. Это локальный адаптер для проверки ML, не присвоение backend-экспорта Мити.

## Последствия

Не ломаем RAG/API/UI; заменяемый клиент и чистые проверки позволяют быстро начать без новых зависимостей. Риски: неверная семантика при буквальном совпадении цитаты, неоднозначные таблицы, OCR-ошибки уже имеющегося слоя, API-лимиты и стоимость, узкий охват, будущая смена контракта. CSV-checker не измеряет научную точность.

План developer:

1. Прочитать solar ZIP README, точные headers и checker; зафиксировать отображение полей, обязательность и enum. Согласовать provisional envelope с Митей отдельно, общий API пока не менять.
2. Реализовать границу PDF/evidence и тесты на пустой текст, неверные ID/bbox, заголовки, неизвестные единицы и ограничения.
3. Добавить подменяемый OpenRouter-клиент и тесты bounded retries, auth failure, schema mismatch, truncation, NaN, отсутствия секретов в логах.
4. Добавить normalizer/validator: cited/primary, scope, FK, несовместимые измерения, PCE и пропуск непроверяемых правил.
5. Добавить staged CSV-export и CLI; тест отказа посередине без видимого частичного комплекта и без перезаписи прежнего результата.
6. На нескольких текстовых dev-PDF вручную проверить связи/цитаты и сравнить с dev_gold, запустить solar checker. Измерить время/стоимость и ошибки по статьям; отдельно заявить неподдерживаемые страницы/документы, не обещать весь корпус.
