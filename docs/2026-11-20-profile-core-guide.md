# Гайд: profile extraction core

Профильное ядро — локальный CLI для извлечения сведений из одного текстового PDF по JSON-профилю. Оно собирает источники, выдаёт offline-кандидаты или отправляет весь доступный текст модели, проверяет ответ и сохраняет JSON/CSV. Solar — предметный адаптер поверх общего ядра. Это отдельный extraction vertical slice, не интеграция с backend, сайтом или UI.

## Установка и конфигурация

Используйте Python и зависимости проекта. Для необязательного Docling-адаптера предназначено отдельное Python 3.11+ окружение; подробности — в [гайде Docling](2026-11-20-docling-adapter-guide.md):

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

```bash
python3.11 -m venv .venv-docling
.venv-docling/bin/python -m pip install -r requirements-docling.txt
```

Режим `scripts` работает offline и не требует ключа. Для `auto` и `model` задайте ключ и конкретную модель OpenRouter:

```bash
export OPENROUTER_API_KEY='...'
export OPENROUTER_MODEL='точный-slug-модели'
```

CLI автоматически не загружает `.env`; переменные должны быть экспортированы в окружение. Модель по умолчанию не задана. Не помещайте ключи в чат, Git, документацию или каталоги результатов. Перед передачей текста PDF внешнему API убедитесь, что это разрешено.

## Запуск

Первый, безопасный offline-проход по солнечной статье:

```bash
.venv/bin/python -m viniti extract-document data/solar/dev/D001.pdf --profile solar --mode scripts -o data/solar/run-001
```

Этот режим пишет `result.json` и `candidates.csv`, не финальные таблицы. Для модельной обработки используйте новый, ещё не существующий каталог:

```bash
.venv/bin/python -m viniti extract-document data/solar/dev/D001.pdf --profile solar --mode auto -o data/solar/run-001-auto
```

`auto` включает локальные кандидаты в контекст, но всё равно выполняет модельный проход, даже если regex нашёл совпадения. `model` запрашивает модель без предварительного script-поиска. В обоих режимах текст отправляется OpenRouter; без `OPENROUTER_API_KEY` и `OPENROUTER_MODEL` (либо `--model`) запуск завершится ошибкой.

Для демонстрационного generic-профиля:

```bash
.venv/bin/python -m viniti extract-document data/solar/dev/D001.pdf --profile custom-example --mode scripts -o data/solar/custom-example-run
```

Либо передайте `--profile path/to/profile.json`. `custom-example` показывает формат профиля и не является третьим научным кейсом.

Общие параметры CLI: `--max-input-chars` (по умолчанию 200000), `--max-tokens` (16000), `--timeout` (90 секунд), `--retries` (2). Результат нельзя перезаписывать: указывайте новый каталог.

Для `--parser docling` доступны `--ocr auto|full|off` и явный флаг `--charts`. OCR требует отдельно установленный Tesseract с `eng`; chart extraction использует локальные дополнительные веса и ресурсоёмок. Не включайте `--charts` без необходимости. См. [гайд Docling](2026-11-20-docling-adapter-guide.md).

## Что описывает профиль

Общий профиль — JSON с `id`, `version`, `tables`; у таблицы есть ключ `key` и `fields`. Поле объявляет тип `text`, `number`, `boolean`, `id` или `reference`, описание и при необходимости `required`. Ссылки указывают другую таблицу профиля. Числовое поле может задавать целевую `unit`, коэффициенты `units`, пределы `minimum`/`maximum` и aliases для ограниченного поиска числовых кандидатов. Числовые пределы проверяются после нормализации; неизвестные настройки и неподдерживаемые типы отклоняются.

Для непустых содержательных значений generic-профиль требует `field_sources`: source ID и дословную цитату; числа также могут указывать исходную единицу и отдельный источник единицы. Локальная проверка подтверждает наличие цитаты и полного числового токена, но не истинность научной интерпретации. ID являются локальными техническими идентификаторами, а не цитатами.

`profiles/solar.json` выбирает `solar_csv`: фиксированный solar-адаптер с точными семью таблицами шаблона и проверками из `solar_facts.py`. У solar сохраняется доказательство уровня записи (`source_ids`, а для результата — фрагмент и страница), не выдумываются field-level источники. После буквальной проверки выполняются нормализация и детерминированные проверки; это не доказательство корректности научной связи или полноты.

## Результаты и оценка

JSON envelope ядра содержит `records`, `candidates`, `tables`, `sources`, `issues`, `coverage` и `run`, а также идентификаторы профиля и документа. Для `scripts` coverage остаётся `partial`, completeness — `not_measured`; отсутствие regex-совпадений ничего не доказывает. Числовые совпадения — лишь кандидаты: скрипт не устанавливает единицы, устройство, экспериментальный контекст или связи.

Успешный model-режим solar-адаптера дополнительно экспортирует семь CSV: `publications`, `materials`, `devices`, `layers`, `measurements`, `results`, `issues`. Это не результат, который выдаёт offline-режим.

Оцениватель сравнивает готовые solar CSV с gold; он не запускает извлечение и не проверяет цитаты против PDF. Команда для одного документа:

```bash
.venv/bin/python -m viniti evaluate-extraction data/solar/run-001-auto docs/materials/solar-participant-kit/dev_gold --publication D001 -o data/solar/evaluation-D001.json
```

Первый аргумент должен быть каталогом с комплектом CSV (например, solar model-результатом); `-o` — новый JSON-файл. Для solar gold лежит в `docs/materials/solar-participant-kit/dev_gold`, а PDF для разработки — в соседнем `dev`. Не подставляйте RAG gold в solar-оцениватель и не смешивайте dev и test-материалы. Оценка считает совпадения результатов с раздельными basic/context ключами и micro/macro сводками; ограничения описаны в самом отчёте и `evaluate_extraction.py`. Это не независимый test-результат.

Локальные ID разыменовываются, а не сравниваются между комплектами. Ненормализованные записи отдельно считаются воздержаниями; соответствующие нормализованные gold-записи остаются пропусками. Scope оценивается отдельно. Macro даёт одинаковый вес статьям; пустые статьи получают нулевые record-метрики, даже если корректно исключены. Допуск `--tolerance` абсолютный, применяется только к значению при совпавшей единице; вычисляется без округления разности. Условия, использованные для сопоставления, и ограничения точности чисел перечислены в JSON-отчёте.

Версии профиля, его hash, режим и модель сохраняются в `run`; после модельного прохода сохраняются также hash запроса и длительность. API-расход и научная точность автоматически из этого не следуют. Сохраняйте каждый прогон в новом каталоге.

## Ручной этап на сайте

Серверная часть ручного профиля уже подключена к `server.py`; экран ещё не реализован.

- `GET /api/profiles` - встроенные и пользовательские профили; `GET|PUT|DELETE /api/profiles/<id>` - чтение, сохранение и удаление. Встроенные `solar` и `custom-example` защищены от перезаписи; пользовательские лежат в `data/profiles/`.
- `POST /api/parse` - PDF и заголовки `X-Profile`, `X-Parser` (`pdfplumber`/`docling`), `X-OCR`, `X-Charts`. Разбор идёт фоновым процессом `parse_document.py`: источники, таблицы, figures, локальные кандидаты и артефакты. Результат - `data/parses/<id>/bundle/`, статус - `job.json`.
- `GET /api/parse/<id>` - статус; `GET /api/parse/<id>/result` - JSON; `GET /api/parse/<id>/file/candidates.csv` и `/file/assets/...` - файлы.

Это разбор без LLM. `auto`/`model` на сайте пока не запускаются; LLM-этап и LLM-аудит подключаются после отладки парсинга. Для Docling задайте `VINITI_DOCLING_PYTHON`; OCR и локальный chart2csv требуют Tesseract и весов моделей. Ошибка парсера завершает job со статусом `error`, частичный результат не публикуется.

## Границы текущей реализации

- По умолчанию `pdfplumber` использует текстовый слой; OCR и изображения доступны только через необязательный Docling-адаптер. Chart extraction — отдельный явный и ресурсоёмкий режим, его данные требуют визуальной проверки. Chunking не реализован; превышение бюджета не приводит к молчаливому усечению. Подробности и ограничения — в [гайде Docling](2026-11-20-docling-adapter-guide.md).
- Нет универсального обнаружения всех полей: script-поиск ограничен aliases числовых полей и метрик профиля.
- Универсальный профиль не обещает произвольный граф сущностей; проверяются только объявленные таблицы и ссылки.
- Это ещё не UI, RAG-профиль или универсальный discovery workflow. Серверные `/api/profiles` и `/api/parse` уже подключены, но экран профиля ждёт выбора прототипа; `static/` пока не менялся.
- Провайдер/ключ/модель не настроены, live-вызов не выполнялся; научная точность и качество на реальных документах неизвестны. Буквальное подтверждение текста не равно научной верификации.

## Основные файлы

- `extraction_core.py` — валидация профиля, script-кандидаты, маршрутизация, нормализация generic-полей и экспорт.
- `extract_document.py` — CLI профильного ядра.
- `profiles/solar.json`, `profiles/custom-example.json` — solar и демонстрационный generic-профили.
- `solar_facts.py`, `solar_extract.py`, `solar_schema.py` — PDF/source-обработка, solar проверки, API-клиент и схема CSV.
- `evaluate_extraction.py` — независимая offline-оценка solar CSV.
- `docs/adr/0002-profile-extraction-core.md` — решение и статус реализации.
