# Backend рабочего пространства «Источник»

Для интеграции фронтенда. Изменения backend не означают, что соответствующие экраны уже подключены.

## Доступ и ошибки

Все пользовательские маршруты требуют cookie-сессию. POST/DELETE/PUT требуют `X-CSRF-Token` и same-origin Origin/Referer согласно существующему auth API. Сессию и токен получает `GET /api/auth/me`. Идентификаторы в URL кодировать через encodeURIComponent. Чужие статьи и разборы возвращают 404. Обычные ошибки: 400 неверный запрос, 401 вход, 403 CSRF/отключённый сетевой разбор, 404 чужой/отсутствующий ресурс, 409 результат не готов, 502 ошибка провайдера, 503 модель/база недоступна.

## Чат

`POST /api/chat`, JSON:

```json
{"mode":"document","document_id":"rag:d001","question":"Что измеряли и при каких условиях?"}
```

Режимы:

| mode | Явно передаваемый контекст |
|---|---|
| document | document_id |
| selection | document_ids: массив от 1 до 12 ID |
| library | библиотека текущего пользователя, не более 12 документов в одном запросе |
| general | без документов |

До 2000 символов вопроса. Ответ содержит `answer`, `citations`, `not_found`, `unverified`, `contradictions`, `context`, `general_knowledge`, `context_key`. В `context`: mode, label, documents, source_count, truncated. Источники ограничены бюджетом; `truncated=true` означает неполный контекст, а не прочитанную целиком библиотеку. Это ограниченный поиск фрагментов, не полноценный семантический индекс корпуса.

Цитата: `ref`, `quote`, `page`, `document_id`, `kind`, `source_id`, `provenance`, `pdf_url`, `anchor_url`. Показывать кликабельную страницу и цитату. Если anchor_url отсутствует, открывать pdf_url. `provenance=recognized` означает распознанный текст, его желательно сверять с изображением PDF.

`unverified=true`: часть ссылок отклонена либо подтверждения нет. Даже `unverified=false` подтверждает только буквальное наличие цитат в переданных фрагментах, а не смысловую корректность каждого утверждения. Не подписывать ответ «научно доказан». `not_found=true`: ответа нет в доступном контексте; это не утверждение, что сведения отсутствуют во всей статье. `general_knowledge=true`: общие знания модели, не вывод по статье.

`contradictions`: topic, refs, documents, explanation. Это предполагаемые моделью расхождения с валидными ссылками, не автоматический вердикт о научной ошибке.

`GET /api/chat?mode=document&document_id=...`: mode, context_key, context_label, history. Для selection передать `document_ids=id1,id2`. История хранится по пользователю и контексту; порядок ID выбранных статей не меняет ключ. Возвращается до 40 последних сообщений, модели передаётся ограниченная история.

`DELETE /api/chat` с теми же query-параметрами удаляет историю только выбранного контекста и пользователя. Паспорт, result.json и CSV чат не меняет.

История хранится в новой идемпотентно создаваемой таблице chat_messages существующей базы, научные таблицы не изменяются.

## Obsidian

- `GET /api/documents/<id>/obsidian.zip`: одна статья.
- `GET /api/obsidian.zip?ids=rag:d001,solar:...`: выбранные статьи.
- `GET /api/obsidian.zip?track=all`: библиотека (допустимы также rag/solar).

Архив содержит README.md, Статьи/*.md, Сущности/<тип>/*.md. В заметках YAML frontmatter, aliases, wikilinks и обратные ссылки. Имя включает устойчивый хеш идентичности, не зависит от порядка выбора статей. Объединяются авторы и наборы данных по нормализованной метке; это сопоставление имён, не внешняя проверка личности автора. Устройства/материалы/измерения имеют область документа. Если старый solar-конверт содержит лишь ID сущности из результата, узел явно говорит, что атрибуты не предоставлены.

До 200 статей в одном экспорте. Прямого доступа к vault нет; архив скачивается пользователем. Граф появляется после распаковки заметок внутри vault. Экспорт не синхронизирует и не перезаписывает заметки. Сводка берётся только из имеющихся данных, дополнительная LLM для экспорта не вызывается.

## Помощник профилей

`POST /api/profile/assist`, JSON:

```json
{"mode":"suggest","profile_id":"universal","question":"Добавь поля для условий эксперимента","sources":[{"page":1,"quote":"Точный фрагмент статьи"}],"history":[]}
```

Вместо profile_id можно передать `profile` с ручным форматом types или исполняемым tables. Переданный profile_id загружается сервером с проверкой доступа, а не из присланного клиентом содержимого. Допустим также profile_id=rag: используется полная предметная схема из паспорта; это не новый исполняемый встроенный профиль RAG.

- suggest: предложения add/modify с помощью модели.
- create: предложения структуры нового профиля; значения и цитаты не выдаются за извлечённые факты.
- audit: детерминированная проверка дублей и структурных пропусков, без вызова модели. Это не оценка предметной полноты профиля.

Ответ: suggestions, audit, profile_source, requires_copy, mode. Каждое предложение: entity, field, type, action, value/example, page, quote, explanation, duplicate. Точность quote и page проверяется по переданным фрагментам, пример очищается при отсутствии подтверждения. Предложения не применяются автоматически. Для requires_copy=true нужно создать пользовательскую копию с новым ID; встроенные профили защищены и на сервере.

Ограничения: вопрос 600 символов, до 24 источников по 600 символов и до 8 предложений. Новая схема сохраняется существующим PUT /api/profiles/<id> после преобразования в tables-контракт и проверки пользователем. Кнопка «применить» должна учитывать action и duplicate, а не добавлять дубли молча.

## Поля профилей и универсальный разбор

См. [полный перечень полей](profile-fields.md). Solar: 94 поля, RAG: 85 полей. Списки получать с сервера, не дублировать в JS.

- GET /api/passport?area=solar или rag: полные таблицы, fields, columns, key и словари.
- GET /api/profiles/universal: исполняемый профиль и summary с типами/описаниями/ограничениями.
- POST /api/parse, PDF body, X-Profile: universal или ID пользовательского профиля.
- X-Parser: pdfplumber либо docling; X-OCR: auto/full/off для docling; X-LLM: off/api.
- Для API-модели нужны настроенные OPENAI_API_KEY/OPENAI_MODEL/OPENAI_BASE_URL либо совместимые OPENROUTER переменные и VINITI_PARSE_LLM=api.
- Ответ 202 с job.id; существующие GET /api/parse/<id> и /result дают статус и исходный разбор. LLM-интерпретация хранится отдельно: /file/llm/interpretation.json. result.json и официальные CSV не переписываются.

Универсальный профиль: studies (объект/метод/условия), results (метрика/значение/единица/условия/связь с исследованием), findings (вывод/ограничение). Любая тема означает независимость схемы от solar/RAG, а не гарантированное понимание любого документа. Без модели это разбор источников и кандидатов, не заполненный научный паспорт.

Реальная проверка на статье LIGO: [отчёт](../reviews/2026-11-22-universal-profile-real-paper.md). Семантическое извлечение настоящей моделью не проверено: в окружении не настроен провайдер.

## Оценка технического качества PDF

`GET /api/documents/<id>/quality`: status, score, components, inputs, limits. При status=insufficient и score=null показывать «Недостаточно данных». Компоненты раскрывать рядом с круговой диаграммой. Это собственная техническая эвристика, не вероятность правильного ответа, не оценка научной достоверности.

Методика и ссылки: [описание оценки](pdf-quality-method.md).

## Состояние передачи

Backend требует интеграции с интерфейсом. Тесты новых chat/obsidian/pdf_quality/assistant изменений в этом продолжении не запускались по условию задачи. Отдельная проверка universal ранее явно запрошена пользователем и описана в отчёте. Коммиты и выкладка не выполнялись.

## Профильные разборы в рабочем пространстве

Готовый универсальный или пользовательский разбор доступен чату с `document_id: "parse:<job.id>"`. Только владелец job со статусом ok может его использовать. GET /api/parse/<id>/pdf открывает оригинал, /quality возвращает техническую оценку, /obsidian.zip скачивает заметку с источниками. В контекст библиотечного режима и общий экспорт входят также готовые самостоятельные разборы; фоновые jobs каталога не дублируются.

Адаптер этих разборов передаёт проверяемые источники. Скриптовые кандидаты не объявляются извлечёнными научными результатами. LLM-интерпретация пока остаётся отдельным артефактом и не переносится в этот конверт: интерфейсу следует отображать её существующим маршрутом /file/llm/interpretation.json. Поэтому Obsidian-экспорт такого разбора содержит источники, но не обещает заполненные таблицы кандидатов.
