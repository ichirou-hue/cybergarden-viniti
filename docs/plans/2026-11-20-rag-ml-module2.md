# План: ML-модуль RAG (предметная область 2)

- **Дата:** 2026-11-20
- **Владелец ML-части:** Илья С
- **Ветка:** `feature/rag-ml` (от `rag`)
- **Границы:** только `rag/` (извлечение, оценка, CLI) и тесты к нему. `server.py`, `static/`, solar-трек и общий backend Мити не трогаем.

## 1. Что требуется по кейсу

Кейс ВИНИТИ, область 2 — Retrieval-Augmented Generation. Нужно превратить PDF-статьи в семь связанных CSV:

| Таблица | Смысл |
|---|---|
| `publications` | библиография + решение о включении |
| `configurations` | конфигурация RAG или baseline (retriever, embedding, chunking, generator, top-k, …) |
| `datasets` | набор, версия, разбиение, язык, домен |
| `tasks` | задача |
| `experiments` | протокол и условия эксперимента |
| `results` | одно значение одной метрики в одном эксперименте |
| `issues` | замечание проверки со ссылкой на результаты |

Ключевые ограничения:

1. Каждая строка `results` — **одно** число, а не среднее по нескольким метрикам.
2. Значение хранится как напечатано (`raw_value`) и нормализованно (`normalized_value`), без догадок.
3. `source_page` — номер страницы PDF с 1; `source_fragment` — дословная цитата со страницы (официальный чекер ищет её в тексте).
4. Неизвестное остаётся пустым; противоречия выносятся в `issues`, а не «исправляются».
5. Формат проверяется `tools/check_submission.py`; полнота и научная правильность им не подтверждаются — для этого нужен свой измеритель.

## 2. Где предел автоматизации

По открытому эталону `dev_gold` (37 616 строк `results`):

- 30 818 (82 %) — оцифрованные точки графиков;
- 5 940 (16 %) — таблицы;
- 858 (2 %) — проза.

Без компьютерного зрения графики недостижимы, поэтому честная цель детерминированного экстрактора — **таблицы + проза**, это ~6 800 строк (18 % эталона). Именно эту часть и надо выжимать; графики отмечать как `present_not_extractable`/`issues`, а не выдумывать.

Три dev-PDF — синтетические сканы (D002, D013, D021): без Tesseract текстового слоя нет. Модуль должен это явно фиксировать, а не молча отдавать пустую статью.

## 3. Архитектура

```
rag/
  pdf.py        чтение страниц, OCR-фолбэк           (есть)
  text.py       нормализация, сравнение чисел        (есть)
  kit.py        поиск комплекта, схема               (есть)
  csvio.py      чтение/запись CSV по схеме           (есть)
  vocab.py      НОВОЕ: метрики, наборы, задачи, единицы
  metadata.py   НОВОЕ: title/authors/year/DOI/scope
  grid.py       НОВОЕ: восстановление таблиц из координат слов
  extract.py    сборка сущностей и строк             (переписать)
  issues.py     НОВОЕ: проверки согласованности
  evaluate.py   измеритель                           (починить сопоставление)
  cli.py        info/pages/extract/sample/evaluate/bench/check
```

### 3.1 `grid.py` — таблицы из координат

`page.get_text("dict")` даёт строки с bbox. Алгоритм:

1. Строка «числовая», если ≥ 2 числовых токена и их доля ≥ 0.4.
2. Таблица — максимальный вертикальный отрезок строк с зазором ≤ 1.8 × высоты строки, содержащий ≥ 2 числовых строки.
3. Колонки — кластеры x-центров чисел (допуск 8 pt).
4. Шапка — строки над первой числовой строкой; ячейки шапки привязываются к колонкам по перекрытию x.
5. Иерархия шапки: уровень 1 (группа/генератор), уровень 2 (набор), уровень 3 (метрика). Одна ячейка, накрывающая несколько колонок, наследуется всеми.
6. Подпись `Table N.` ищется ближайшей строкой; оттуда берутся протокол и единицы.

Так закрываются оба основных случая: многоуровневая шапка (D001: генератор × набор × метрика) и плоская (D010: строка = набор, колонка = метрика).

### 3.2 `vocab.py` — словари

- метрики: EM, F1, Accuracy, Precision, Recall, AUC, NDCG@k, MRR@k, MAP@k, Hit@k, ROUGE-L/1/2, BLEU, KP/KR/KF1, faithfulness, answer relevance, latency;
- единицы: fraction, %, score, ms, s, points, count;
- наборы: HotpotQA, 2WikiMultihopQA, MuSiQue, Natural Questions, TriviaQA, WebQuestions, MS MARCO, BEIR, FEVER, SciFact, WoW, SQuAD, PubmedQA, MMLU, MIRAGE, FeB4RAG, KILT, ELI5, ASQA, QAMPARI;
- задачи: QA (open-domain/multi-hop/биомедицинский), fact verification, dialogue generation, code generation, retrieval evaluation, evaluator quality.

### 3.3 `metadata.py`

Заголовок — самая крупная строка первой страницы до «Abstract»; авторы — строки с инициалами/аффилиациями до аннотации; год — из шапки конференции или копирайта; DOI — регуляркой; `in_scope=true` (исключения — только при явном признаке вне области, например solar).

### 3.4 `extract.py`

Порядок: метаданные → проза (наборы, задачи, конфигурация по умолчанию) → таблицы → прозаические результаты → проверки.

Правила:
- конфигурация строки таблицы = (метка строки, группа шапки), иначе (метка строки), иначе одна конфигурация из прозы;
- набор = уровень шапки, иначе метка строки, если она совпала со словарём;
- метрика = глубочайший уровень шапки; `k` из `@k`;
- `raw_value` — как напечатано, `metric_value` — с ведущим нулём, `metric_unit` — по шапке/значению;
- `source_fragment` — текст строки таблицы (label + числа), дословно из PDF;
- `source_page`, `source_table` — из подписи.

### 3.5 `issues.py`

Детерминированные проверки: значение вне шкалы, отсутствие единицы, `%` против п.п., конфликт значений одной конфигурации, падение Recall@k с ростом k, конфликт размера выборки, скан без текстового слоя, «результатов не найдено». Каждая ссылается на `record_ids`.

### 3.6 `evaluate.py` — починить сопоставление

Сейчас `results` сопоставляются по внутренним `config_id`/`dataset_id`, которые у эталона и предсказания всегда разные, поэтому F1 = 0 даже при верных числах. Меняем сигнатуру на семантическую: (публикация, вариант, генератор, набор, задача, метрика, k, вариант метрики), с подстановкой имён из связанных таблиц. Дополнительно остаётся режим «по значению».

## 4. Проверка

1. `python -m rag selfcheck` — эталон против себя = 100 %.
2. `python -m rag extract --split dev --out out/submission` — все 21 статьи.
3. `python -m rag check --submission out/submission` — официальный чекер (ошибок структуры быть не должно).
4. `python -m rag bench` — прогон dev + отчёт по таблицам и публикациям + JSON.
5. `python -m unittest discover tests` — юнит-тесты парсера шапки, метрик, чисел, issues.

## 5. Что осознанно не делаем

- оцифровку графиков (нужен CV-пайплайн и ручная калибровка осей);
- OCR без установленного Tesseract (фиксируем как ограничение, `--ocr` остаётся);
- LLM-доразметку (нет ключей/квот в репозитории; детерминированный результат воспроизводим);
- backend-контракт и фронтенд — не наша зона.
