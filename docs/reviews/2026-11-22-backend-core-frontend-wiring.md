## Вердикт

**Нужны правки.** Архитектура и проводка в порядке: владелец документа, CSRF,
same-origin, фильтрация каталога/задач и per-user профили работают, конфликты
слияния разрешены корректно, все тесты и UI-проверки зелёные. Но есть три
блокера коммита:

1. `auth.py` и `tests/auth/` не в git, а `db.py` их импортирует - чистый checkout
   и CI падают на импорте (B1);
2. документированный ограничитель входов не работает вообще: `auth_failures`
   всегда пуста (B2);
3. `auth` создаёт файл `data/viniti.sqlite3` побочным эффектом, из-за чего
   `/api/results`, `/api/issues` и `/api/stats` на неинициализированной базе
   перестают отвечать 503 и валятся с обрывом соединения (B3).

## 🔴 Блокеры коммита

### 🔴 B1. `auth.py` и `tests/auth/` не добавлены в git

`git status`: `auth.py`, `tests/__init__.py`, `tests/auth/` - untracked, в
`.gitignore` их нет. При этом `db.py:29` делает `import auth`, а `db.py`
импортируют `server.py`, `batch.py`, `pipeline.py`, `export_csv.py`. Если
закоммитить только правки отслеживаемых файлов, чистый checkout и CI упадут на
`ModuleNotFoundError: auth`.

Отдельно про тесты: `python -m unittest` не находит подкаталог без
`__init__.py` (проверено на минимальном примере: подкаталог без `__init__.py` -
`Ran 0 tests`). То есть `tests/__init__.py` и `tests/auth/__init__.py` обязаны
попасть в git, иначе `tests/auth/test_auth.py` (7 тестов) и `tests/test_rag_api.py`
(5 тестов, до этой правки он вообще не собирался) молча выпадут из CI.

Предложение: добавить `auth.py`, `tests/__init__.py`, `tests/auth/__init__.py`,
`tests/auth/test_auth.py` в тот же коммит.

### 🔴 B2. Ограничитель неудачных входов не работает, `auth_failures` всегда пуста

`auth.py:127-136`. Внутри `with self.connect() as conn` неудачная попытка
пишется в `auth_failures` (`:135`), а сразу после этого `raise AuthError(...)`
(`:136`). Исключение проходит через `__exit__` соединения, тот делает ROLLBACK,
и INSERT откатывается. Проверка `count >= 5` (`:129-131`) поэтому никогда не
срабатывает.

Замер на живом сервере: шесть запросов `/api/auth/login` с неверным паролем дали
`401, 401, 401, 401, 401, 401`, а затем верный пароль пустил с `200`. Прямой
вызов `Auth.login` семь раз подряд на одном `username_key` даёт то же самое, и
после этого:

```
auth_failures rows: 0
```

Почему важно: это не косметика. В `AGENTS.md:279` (`auth_failures` - ограничитель
неудачных входов) и в комментарии к схеме ограничитель заявлен как рабочая
защита, а по факту подбор пароля ничем не ограничен. Тестов на него нет, поэтому
CI этого не видит.

Предложение: фиксировать неудачу до `raise`, например отдельным
`with self.connect() as conn: conn.execute("INSERT INTO auth_failures ...")` (или
`conn.commit()` перед `raise`). К тому же `DELETE FROM auth_failures ...` на
`:128` стоит сделать в том же соединении, где считается `count`.

Два следствия, которые надо решить вместе с фиксом:

- `auth.py:129` считает попытки по паре `(username_key, client)`, а `client` -
  это `self.client_address[0]`. Сервер слушает только `127.0.0.1`
  (`server.py:1422`) и не смотрит `X-Forwarded-For`, то есть у всех клиентов
  один `client`. После фикса пять неверных попыток будут блокировать вход любому
  пользователю этого узла на 15 минут - подбор превращается в простой способ
  заблокировать чужой аккаунт;
- `server.py:262` (`auth_register`) после создания пользователя сразу вызывает
  `store.login`, а тот с работающим ограничителем может ответить 429: аккаунт уже
  создан, а клиент видит ошибку и не получает сессию. Регистрации стоит обходить
  счётчик неудач.

### 🔴 B3. `/api/results`, `/api/issues`, `/api/stats` падают с обрывом соединения на неинициализированной базе

`server.py:141-145` (`data_connection`) считает базу подключённой, если файл
существует, а `db.connect` (`db.py:251-259`) только открывает файл и схему не
создаёт. До этой правки файл `data/viniti.sqlite3` появлялся лишь после
`db.py --init`, поэтому на чистом checkout пользователь получал понятный 503
«База результатов не подключена. Запустите python db.py --init...».

Теперь `server.py:1425` (`server.auth = auth.Auth(args.data)`) и первый же
`/api/auth/register` создают этот же файл - с таблицами `users`/`sessions`, но
без таблиц результатов. Воспроизведено на чистом каталоге:

```
до регистрации:  /api/results  -> 503, файла базы нет
после регистрации: файл есть (48 КБ, только auth-таблицы)
  /api/stats                    -> 000 (соединение закрыто)
  /api/issues?area=rag          -> 000
  /api/results?area=rag&table=results -> 000
  /api/passport                 -> 200
```

В лог уходит `sqlite3.OperationalError: no such table: rag_results`. У
`BaseHTTPRequestHandler` нет верхнего перехвата, поэтому клиент вместо JSON и
диагностики получает пустой ответ. Сценарий реалистичный: инструкция в README и
`AGENTS.md` начинается с `db.py --init`, но ничего не мешает открыть сайт,
зарегистрироваться и пойти в «Паспорт»/конструктор (`static/constructor.js:339`
ходит в `/api/results`).

Предложение: в `data_connection` проверять не файл, а наличие таблицы
(`SELECT 1 FROM sqlite_master WHERE type='table' AND name='documents'`) и
по-прежнему отвечать 503 с подсказкой про `db.py --init` и `import_gold.py`.

## 🟡 Стоит исправить

### 🟡 S1. UI-мок не проверяет ни CSRF, ни сессию на рабочих маршрутах

`tools/mock_api.py:29` держит один фиксированный `MOCK_CSRF` и нигде его не
сверяет, `/api/documents`, `/api/demo`, `/api/profile/source` и
`/api/profile/assist` сессию не требуют вообще (`tools/mock_api.py:687-710`).
Поэтому проверки `harness 41/41`, `auth 41/41`, `manual-profile 18/18`
пройдут и в том случае, если из `static/api.js` убрать заголовок
`X-CSRF-Token` или из `static/profile.mjs` - `apiFetch`: живой сервер ответил бы
403, а мок - 200. Это ровно тот класс регрессии, ради которого переписывался
фронтенд.

Предложение: в мок добавить проверку заголовка для изменяющих маршрутов (403 при
несовпадении, как в `require_user`) и 401 без cookie на `/api/documents`,
`/api/parse`, `/api/profile/*`. Тогда `auth.mjs` начнёт проверять проводку
CSRF, а не только экран.

### 🟡 S2. Нет тестов на ограничитель, same-origin и истечение сессии; тест выхода не проверяет тело

- ограничитель входов не покрыт ничем, поэтому B2 дожил до ревью;
- same-origin (`server.py:219-228`) не покрыт: 403 на чужой `Origin` проверен
  только руками;
- истечение сессии проверяется лишь косвенно (нет теста с `Auth(clock=...)`);
- `tests/auth/test_auth.py:126-128`: после `logout` запрос `/api/auth/me`
  проверяется только по коду 200, тело игнорируется. Если выход перестанет
  убивать сессию, тест останется зелёным. Проверено вручную, что сервер сейчас
  ведёт себя правильно (старая cookie -> `{"user": null}`), но тест это не
  фиксирует. Нужно `self.assertEqual(body, {"user": None})` и повторный запрос
  со старой cookie.

### 🟡 S3. `shared_document` опознаёт общий документ по суффиксу `:demo`

`server.py:175-182`: `str(document_id).endswith(":demo")`. Сейчас на практике
достижим только `rag:demo` (все прочие id собираются как `<track>:<slug>-<hash8>`
в `rag_api.py:703` и `solar_api.py:275`), но проверка не привязана к области и
формату id. Если формат id изменится или появится второй демо-id, любой id с
таким хвостом автоматически станет доступен всем вошедшим и будет обойдён в
`claim_uploaded_document` (`server.py:200-213`) без записи в `document_owners`.
Предложение: явный набор/константа (`SHARED_DOCUMENTS = {"rag:demo"}`) или
сравнение с полным id.

### 🟡 S4. `legacy_paper` закрывает всё, когда auth не настроен, и дважды матчит регулярку

`server.py:1153-1159`:

```python
paper_id = PAPER.fullmatch(path).group(1) if PAPER.fullmatch(path) else None
if not paper_id or not self.owns_document("rag", paper_id):
```

`owns_document` (`server.py:184-190`) возвращает `False`, если `auth_store()` нет,
а `documents_get` в том же состоянии (`server.py:913-918`) ownership не проверяет
вовсе - то есть без auth-хранилища `/api/documents/<id>` открыт, а
`/api/papers/<id>` всегда 404. Тесты этого не ловят, потому что все серверные
тесты теперь ставят `server.auth`. Плюс сам `fullmatch` вызывается дважды.
Предложение: `match = PAPER.fullmatch(path)`, отдельная ветка для «auth не
настроен», и решение о поведении зафиксировать в AGENTS.

### 🟡 S5. Старые пользовательские профили становятся невидимыми без миграции

`server.py:349-356`: корень профилей теперь `data/profiles/<user_id>`
(`profile_root_for`), а `profiles_store.load/save` кладут файлы прямо в `root`.
Профили, сохранённые до этой правки (`data/profiles/<name>.json`), после входа
не находятся: `GET /api/profiles/<name>` - 404, в списке их нет. Файлы не
удаляются, но и не мигрируются. В комментариях и AGENTS об этом ни слова.
Предложение: либо одноразовый перенос при первом входе, либо строка в AGENTS
«профили, сохранённые до пользовательских каталогов, нужно перезалить»,
либо fallback на плоский каталог при чтении.

### 🟡 S6. `parse_get` и `parse_post` берут сессию дважды и доверяют ей без проверки

`server.py:466-473`: `session = self.current_session()`, затем
`session["user"]["id"]`. Диспетчер (`server.py:1238-1241`) уже вызвал
`require_user`, так что на практике `session` не `None`, но при истечении cookie
между двумя вызовами получится `TypeError` -> 500 вместо 401. Проще
протянуть `session` из диспетчера, как сделано для `documents_post`/`documents_stream`.

## ⚪️ Мелочи и вкусовое

- `server.py:1225-1234`: ветки `/api/demo` и `/api/documents` идентичны после
  правки (обе `require_user()` + `documents_post(path, session)`), внешний `if`
  с внутренним `if path == "/api/demo"` ничего не меняет. Слить в один вызов.
- `auth.py:91-92`: `int(os.environ.get("VINITI_AUTH_ITERATIONS"))` и
  `...SESSION_TTL` без перехвата. Битая переменная окружения уронит `main()` с
  трейсбеком вместо внятного сообщения. `hash_password` при этом валидирует
  диапазон итераций, а сам параметр - нет.
- `auth.py:55-61`: `PRAGMA user_version` теперь принадлежит auth, хотя база
  общая с результатами. Пока другие модули его не используют
  (`grep user_version` - только `auth.py`), но первый же модуль, который захочет
  свою версию миграций, столкнётся.
- `auth.py:96-103`: `connect()` на каждом обращении выполняет `executescript(SCHEMA)`
  и `PRAGMA journal_mode=WAL`, а `authenticate` (`:158`) пишет `last_seen_at` на
  каждый запрос. На один запрос к карточке выходит 2-3 соединения и запись в БД.
  Для демо терпимо, но это лишняя работа на каждый GET.
- `auth.py:85`: для несуществующего пользователя PBKDF2 не считается (ранний
  `return` в `:133`), время ответа различается. Утечка ограничена: `register`
  всё равно отвечает 409 «имя занято».
- `server.py:175-182` и `README.md:76`, `AGENTS.md:202`: «`rag:demo` виден всем»
  неточно, анонимный запрос получает 404 (`owns_document` требует сессию).
  Виден всем, кто вошёл.
- `README.md:76`: «Истёкшая cookie превращает любой запрос в 401» - чтение
  каталога без сессии отдаёт 200 и пустой список (`server.py:882`), 401 только у
