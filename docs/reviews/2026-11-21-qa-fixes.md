## Находки

### 🟡 1. `locateResult()`: устаревший результат пишет в `#status` сообщение с пустым ID и не отменяется при смене фильтра/страницы

**Где:** `static/document.js:455-475` (сама функция), `static/document.js:565-581` (точка вызова).

**Проблема.** После `await locateResult()` нет повторной проверки `id !== request` / `ctx.signal.aborted`, а сам поиск читает **живое** `state.result` на каждой итерации:

```js
const index = chunk.items.findIndex(item => item.result_id === state.result);
```

**Сценарий (воспроизводим без сети):**
1. Открыть `#/doc/rag:d020?track=rag&result=R060` — страница 1 отрисована, `load()` запустил `locateResult()`, идёт последовательный скан кусков по 200 (до 5 запросов).
2. Пока скан идёт, пользователь нажимает «Далее» (`document.js:545`: `state.result = ""; state.page += 1;`) или меняет фильтр/поиск (`:394`, `:443`, `:450` — все обнуляют `state.result` и вызывают новый `load()`).
3. Старый `locateResult()` продолжает работать, `findIndex` со `state.result === ""` не находит ничего, доходит до `return 0`, и `:579` пишет в статус: **«Запись  не найдена среди первых 1 000 результатов.»** (двойной пробел, пустой ID).

**Ожидание:** устаревший поиск молча прекращается, когда пользователь ушёл из этого состояния; сообщение всегда содержит реальный ID записи, которую искали.

**Факт:** лишние до 5 запросов по 200 строк и ложное сообщение об ошибке в статусной строке (она живёт до следующего `say("")`, то есть до навигации).

**Почему важно:** это единственный видимый пользователю побочный эффект новой фичи; на медленном соединении окно в 5 запросов вполне достижимо быстрым кликом.

**Предложение:**
- захватить `const wanted = state.result;` в начале `locateResult()` и использовать локальную переменную и в `findIndex`, и в тексте сообщения;
- после `await locateResult()` (и внутри цикла на каждой итерации) проверять `if (id !== request || ctx.signal.aborted) return;` — `id` уже есть в `load()` (`:479`);
- `catch` в `:465-468` различать не только `AbortError`: сетевой сбой сейчас неотличим от «не найдено», хотя ожидание из QA — «обработка ошибок». Достаточно вернуть `-1` и отдельным сообщением сказать «Не удалось проверить страницы».

**Дополнительно (тот же блок):** если `found === state.page`, но `tr.target` так и не появился (например, бэкенд проигнорировал `offset`), код молча ничего не делает: ни подсветки, ни сообщения. Стоит добавить ветку «не удалось показать запись» — иначе поведение неотличимо от «страница отрисована нормально».

### 🟡 2. Паспорт: выбранная строка может остаться вне окна в 200 строк — карточка показывает строку, которой нет в таблице

**Где:** `static/passport.js:296-297` (`selected` сохраняется, `visible` режется), `static/passport.js:356-360` (`repaint()` сбрасывает `shown` в 200).

**Сценарий:**
1. Импортировать `/api/documents/rag:d020/export.json` (408 строк).
2. Дважды нажать «Показать ещё» (`shown = 600`), выбрать строку с индексом 300.
3. Изменить фильтр «Проверка» (или начать печатать в поиске) так, чтобы строка осталась в `filtered` (например, переключить «Все» → «Все», событие `change` вызывает `repaint()` → `shown = 200`).

**Ожидание:** либо окно расширяется до выбранной строки, либо выбор переносится на первую видимую строку; таблица и карточка всегда согласованы.

**Факт:** `filtered.includes(selected)` истинно, поэтому `selected` не сбрасывается, но `filtered.slice(0, 200)` его не содержит. В результате:
- ни у одной строки нет `aria-pressed="true"` и `.selected`, то есть таблица выглядит «ничего не выбрано»;
- правая карточка (`#detail`) показывает данные невидимой строки;
- `syncActions()` (`:344-348`) включает «Привязать исходный PDF» для невидимой строки.

**Почему важно:** это новый режим взаимодействия, введённый в этой же правке, и рассинхрон таблицы с карточкой читается как баг, а не как ограничение.

**Предложение:** в `drawRows()` после вычисления `filtered` добавить
`const index = filtered.indexOf(selected); if (index >= shown) shown = Math.ceil((index + 1) / PAGE_SIZE) * PAGE_SIZE;`
(или, наоборот, при сбросе окна явно переводить `selected` на `filtered[0]`). Второй вариант дешевле, но сбрасывает выбор пользователя.

### 🟡 3. Вкладка «Замечания» по-прежнему молча обрезает выдачу на 200 — тот же дефект, что чинили для «Фрагментов PDF»

**Факт:** `limit: 200` и счётчик `Замечаний: ${data.total}` без пометки об обрезке. В QA-отчёте этот пункт был явно отмечен («Аналогичный жёсткий `limit: 200` есть у вкладки „Замечания“»), но правка закрыла только `/sources` (`:755-762`).

**Почему важно:** контракт `/issues` в моке разрешает до 500 (`tools/mock_api.py:473`), на реальных данных Solar в `dev_gold` уже 53 замечания, на больших документах счётчик так же начнёт врать. Это ровно тот класс дефекта, который правка обязалась закрыть, и оставлять соседнюю вкладку в старом виде — непоследовательно.

### ⚪ 4. Счётчик паспорта смешивает окно с нефильтрованным итогом

**Где:** `static/passport.js:338-341`.

**Факт:** `Показано ${min(shown, filtered.length)} из ${rows.length}` + `· ещё ${filtered.length - shown}`. При фильтре, оставляющем 250 строк из 969, получается «Показано 200 из 969 · ещё 50» — 200 + 50 ≠ 969, читается противоречиво. До правки в знаменателе была отфильтрованная длина (`Показано 250 из 969`), то есть семантика знаменателя поменялась без предупреждения.

**Предложение:** `Показано 200 из 250 (всего 969)` — окно, отфильтрованное количество и полный объём раздельно.

### ⚪ 6. Битый `/source/`: диалог закрывается, но URL остаётся указывать на несуществующий источник

**Где:** `static/app.js:181-186`.

**Факт:** `dismissEvidence()` закрывает диалог с `silent = true` (`static/evidence.js:15-19`), поэтому обработчик `close` (`:30-41`) не переписывает hash. В адресной строке остаётся `#/doc/rag:d020/source/999999`, а сообщение живёт только в `#status`. F5 повторяет ошибку, ссылку нельзя переслать без неё.

**Предложение:** после `dismissEvidence()` в `catch` заменить hash на `docHash(docId)` (или `#/doc/...` без `/source/`) через `history.replaceState`. Заодно это делает поведение одинаковым с обычным закрытием диалога по Esc.

**Проверено, что побочных закрытий нет:** `dismissEvidence()` вызывается только в этом `catch`; при закрытом диалоге она выходит по `if (!dialog.open) return` и не трогает `silent`/`entryHash`; закрытие «своего» диалога при переходе на другой `/source/` исключено, потому что навигация по `/source/` не проходит через `dismissEvidence()` в начале `route()` (`app.js:123`).

### ⚪ 7. `#/doc/foo`: область берётся из «последней активной», URL не нормализуется

**Где:** `static/app.js:144-146`.

**Факт:** для ID без префикса `desired = params.track || app.track`. Сейчас это безопасно (все реальные `document_id` в моке и в `uploadPDF` имеют вид `<track>:<slug>`, `tools/mock_api.py:621`), и поведение «документ не найден» корректно. Но смысл ссылки зависит от истории навигации: при появлении второго дескриптора (Solar) один и тот же `#/doc/foo` без `?track=` откроется в разных областях у разных пользователей, а hash не нормализуется (нормализация в `:164-166` срабатывает только когда `params.track` уже есть).

**Предложение:** при отсутствии префикса либо подставлять `?track=` в URL, либо пробовать дескрипторы по очереди и показывать «документ не найден» только если не подошёл ни один. Как минимум — комментарий, что `app.track` здесь fallback «по истории».

### ⚪ 8. `unit: "unspecified"` проверяется только в `unit`, но не в `normalized_unit`

**Где:** `static/passport.js:75-77`.

**Факт:** значение теперь не теряется (это правильно), а единица гасится только для `entry.unit`. Если экспорт придёт с явным `normalized_unit: "unspecified"` (сам по себе контракт этого не запрещает), в таблице и карточке появится «0.42 unspecified» — служебная метка утечёт в UI. `rag_facts.py:56` кладёт `unspecified` только в `unit`, так что на текущих данных это не воспроизводится.

**Предложение:** нормализовать оба поля одной функцией: `const cleanUnit = value => (value === "unspecified" ? undefined : value)`.

## Что проверено и претензий нет

**`static/document.js`**
- `locateResult()` (`:455-475`): страница считается корректно — `floor((offset + index) / PAGE) + 1` при `PAGE = 50`; фильтры передаются те же, что и в `load()` (`:460-464` против `:489-493`), поэтому индексация согласована; `issues` передаётся в том же формате `"1"/""`.
- Границы окна поиска честные: цикл `offset < 1000` шагом 200 покрывает ровно первые 1000 записей, ранний `break` при `offset + chunkSize >= chunk.total` не даёт лишнего запроса, текст сообщения (`:579`) совпадает с фактическим объёмом скана. `number(1000)` даёт «1 000» — читается нормально.
- Запрос по 200 строк не превышает серверный максимум: `page_args(..., maximum=200)` (`tools/mock_api.py:256-257, 463-468`).
- `AbortError` в `locateResult` пробрасывается, `finally { locating = false }` (`:571-573`) сбрасывает флаг и при исключении — повторного входа и зацикливания «locating» нет; защита `found !== state.page` (`:574`) исключает бесконечную перезагрузку на детерминированных данных (порядок выдачи в моке стабилен: `all_rows` + фильтр без пересортировки). Остаточный риск при живом бэкенде с нестабильным ранжированием описан в находке 1.
- «Фрагменты PDF» (`:755-762`): `limit=500` — это ровно максимум контракта `/sources` (`tools/mock_api.py:473`), счётчик сравнивает `items.length` с `total`, поэтому пометка «показаны первые N» появится и в случае, если бэкенд отдаст меньше запрошенного. На D020 (408+3=411) пометки не будет, на D014 — будет; ожидания `e2e.mjs:68-82` сходятся с фикстурой.
- Пагинация результатов и очистка `state.result` во всех точках смены фильтров/поиска/страницы (`:394, :443, :450, :545, :551`) — консистентно.

**`static/passport.js`**
- `csvCell()` (`:152-157`): ведущие пробелы/переводы перед `= + @ -` теперь ловятся (`/^\s*[=+@-]/`), отдельная ветка `/^[\t\r]/` закрывает таб/CR перед «безопасным» символом; числа не ломаются — `-5`, `-1.2e-3`, `1,5`, `"  -5"` проходят числовую регулярку и остаются без апострофа, то есть в Excel остаются числами; `" =cmd"`, `"- 5"`, `"@SUM(1)"`, `"\t=1+1"` экранируются. Регрессии против прежнего поведения (`=cmd` и раньше экранировался) нет.
- `unit: "unspecified"` (`:75-77`): значение больше не теряется, служебная единица не попадает в UI, `value()` (`:147-150`) склеивает «0.42» без хвоста. Для `facts` из `rag_facts.py` такие записи одновременно получают замечание `missing_unit` → статус «На разборе», то есть скрытие превратилось в корректную пометку.
- Окно строк: `PAGE_SIZE = 200`, `repaint()` сбрасывает `shown` на всех трёх фильтрах (`:357-366`), срез и `Math.min(shown, filtered.length)` дают правильные числа на границе (250 → «250 из 250», без лишней кнопки); «Показать ещё N» считает остаток (`Math.min(PAGE_SIZE, filtered.length - visible.length)`), на последнем куске покажет «8», а не «200».
- CSV (`:159-173`) собирается из всех `rows`, независимо от окна и фильтров — окно не может «потерять» строки экспорта; `syncActions()` от `shown` не зависит.
- Остальное: `passportRows`, `validation`, `download`, работа с `blob:` PDF — без изменений в этой правке.

**`static/app.js`**
- `dismissEvidence()` в `catch` (`:184`) — см. находку 6; побочных закрытий нет.
- `desired` (`:144-146`): для `rag:d020` поведение не изменилось (префикс всё ещё главнее `?track=`), для ID без префикса больше не выводится ложное «Раздел foo не подключён», нормализация `?track=` при наличии параметра сохранена (`:164-166`).

**`static/index.html`, `static/style.css`**
- RAG и «Паспорт» в одном `.track-switch` (`index.html:19-22`): `#tracks` — отдельный вложенный контейнер, поэтому `renderTracks()` не затирает ссылку «Паспорт»; `aria-current="page"` ставится/снимается в `route()` (`app.js:122, 133`), у RAG остаётся `aria-pressed`.
- Специфичность проверена: `.track[aria-current="page"]` (0,2,0) и `.track.active` (0,2,0) дают одинаковый вид; на hover их перекрывает `.track:hover:not(:disabled)` (0,3,0), но сгруппированное правило `.track[aria-current="page"]:hover` объявлено ниже и той же специфичности — активная вкладка не «гаснет» под курсором. `a { color }` (0,0,1) не перебивает `.track` (0,1,0). `:focus-visible` задан глобально (`style.css:29`), ссылка-вкладка его получает.
- Мобильные правила `passport-table` (`:432-446`): `table.passport-table` (0,1,1) объявлен ниже `.results table { min-width: 720px }` (`:249`) и внутри `@media`, поэтому `min-width: 0` и `table-layout: fixed` действительно применяются; ширины `th:nth-child` суммарно 100 %, `hyphens: auto` работает при `lang="ru"` (`index.html:2`); `.results table { min-width: 0 }` (`:422`) при этом не ломает `table.results-table`/`catalog-table`, которые восстанавливают свои `min-width` более поздними правилами (`:423-424`). Скрытие `.track-switch` на паспорте убрано (`:65`), скрытым остался только `#upload` — импорт на паспорте по-прежнему доступен через кнопку в герое (`#passport` внутри скрытой формы, программный `.click()` работает).

**`tools/uitest/*`**
- Ослабления проверок нет: все удалённые `check(...)` — перенос/замена, новая версия строже (например, `beforeTitle` **и** `beforeRows` вместо одного текста; `normalized_value` в CSV вместо `some(valueColumns)`; `ids.includes(...)` по разобранному CSV вместо подстроки в тексте файла).

- `e2e.mjs:68-104` добавлены реальные проверки на живых фикстурах (411 фрагмент, обрезка на D014, `result=R060` → страница 2, закрытие диалога при битом `/source/`, `#/doc/foo`); ложноположительных не вижу: `результат=` проверяет одновременно `tr.target` и текст счётчика, битый source — и состояние диалога, и сообщение.

## Что не проверено

- **Прогоны тестов не выполнялись.** `harness.mjs`, `e2e.mjs`, `passport.mjs` требуют запущенного мока на `:8799`; по условию задачи серверы не поднимал. Заявленные в QA-отчёте результаты (`passport.mjs` 145/145, `e2e.mjs` 24/24, `harness` 43/43) приняты на веру и по коду выглядят правдоподобными.
- **Реальный бэкенд Мити** (`/api/documents`, `/results`, `/sources`) — проверял по контракту мока. Ключевое допущение: он чтит `offset` и `limit ≤ 200` для `/results` (это уже было нужно прежнему пагинатору) и `limit ≤ 500` для `/sources`. Если `limit` в `/sources` клампится ниже 500, UI покажет честную пометку, но 500 строк не получит.
- **Firefox/Safari**, реальный рендер мобильной таблицы на длинных неделимых строках (`table-layout: fixed` не даёт таблице расти, но содержимое ячейки без `overflow-wrap` может вылезти за границу) — только рассуждение по коду.
- **Поведение `locateResult` при живом, нестабильно упорядоченном ранжировании** — риск описан, но воспроизвести без бэкенда нельзя.
- **Производительность окна** на 28 649 строках в браузере (`drawRows` перефильтровывает весь массив на каждый клик «Показать ещё») — по коду это O(n) на клик, приемлемо, но замеров нет.
