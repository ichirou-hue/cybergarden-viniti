## Первоначальные находки (история; актуальный статус ниже)

- 🔴 `extraction_core.py:323,329–332,371–379` — offline-экспорт любого обычного fields-профиля падает. `run(..., mode="scripts")` возвращает непустые `columns`, но `tables={}`; `export_result` до записи `candidates.csv` обращается к `result["tables"][table]`. Для штатного `custom-example` это `KeyError: 'equipment'`, который CLI также не перехватывает. Следовательно, документ с пользовательским профилем в режиме по умолчанию невозможно выгрузить даже при корректном PDF. Предложение: в scripts экспортировать только JSON и candidates, не обходить предметные таблицы. Добавить CLI-тест `--profile custom-example --mode scripts`, включая документ без совпадений; существующий offline CLI-тест проверяет только solar с пустыми `columns`.

- 🔴 `extraction_core.py:97–99,285` — коэффициенты профиля проверяются одним парсером, а применяются другим. Например, `units={"°C": "0,1"}` успешно проходит `decimal(factor)`, но `Decimal(factor)` при нормализации выбрасывает `decimal.InvalidOperation`. Обработчик ловит только `ValueError`; вместо результата или диагностического отказа будет traceback. То же расхождение возможно с Unicode-записью числа, которую нормализует `clean`. Предложение: применять тот же `decimal(factor)` либо канонизировать коэффициенты при компиляции; альтернативно явно запрещать такие формы в профиле. Регрессия должна проверить весь путь compile → run → export с коэффициентом `"0,1"`, а не только compile.

- 🔴 `solar_facts.py:260–269` — относительная процентная неопределённость по-прежнему принимается за абсолютный spread в `raw_unit`. Для источника `Voc = 1000 mV (±2%)`, кандидата `raw_value="1000"`, `raw_unit="mV"`, `spread_value="2"` проверки проходят: regex после `2` запрещает только `[\w.,]`, но разрешает `%`. Экспорт получает `1 V` и `spread_value=0.002`, хотя 2% от 1 V — 0.02 V; по текущему контракту относительный spread вообще должен оставаться в note. Инструкция модели не защищает от такого ответа. Предложение: проверять контекст и шкалу именно выражения неопределённости; явный `%`/relative либо неоднозначный spread сохранять только в note с issue, не пересчитывая как mV. Добавить негативный тест этого примера рядом с положительным `1000 ± 20 mV`. Старое замечание о пересчёте абсолютного spread исправлено, но закрывать весь риск неопределённости пока рано.

- 🟡 `extraction_core.py:82–88,135–141,227–239` — профиль может объявить обычное поле `field_sources`, зарезервированное транспортным контрактом. `compile_profile` его принимает, а `response_schema` молча заменяет схему строкового поля объектом provenance. Если модель возвращает этот объект, validator затем читает его как значение объявленного поля; для типа `text` это доходит до `clean(dict)` и `TypeError`. Строковое значение, наоборот, не проходит проверку provenance. Предложение: запрещать `field_sources` как имя поля при компиляции (в том числе как key), либо вынести данные и provenance в разные пространства имён. Тестировать отказ до вызова model_client.

- 🟡 `extraction_core.py:55–56,87,91,94–95` — часть malformed JSON-профилей вызывает непредусмотренный `TypeError` вместо диагностического `ValueError`: например, `adapter=[]`, `type=[]`, `reference=[]`. Также `unit=[]`/объект может использоваться как ключ словаря в вычисляемом аргументе `setdefault` ещё до проверки типа; аргумент вычисляется даже при наличии `units`. CLI ловит только `OSError`/`ValueError`. Предложение: сначала проверять типы adapter/type/reference/unit, затем membership и построение defaults; добавить параметризованные тесты null/list/object и CLI-тест без traceback. Не нужно просто перехватывать все исключения, скрывая программные ошибки.

- 🟡 `solar_facts.py:287–295` — `time_point` нормализуется без проверки буквального значения и единицы в evidence. В обычной fixture можно добавить результату `time_point="999"`, `time_unit="h"` без изменения источников: экспорт выдаст подтверждённое на вид время, а `check_consistency` использует его для разделения групп (`:310–313`), из-за чего соответствующий результат выпадет из J–V проверки. Это тот же класс проблемы, что уже исправлен для bandgap/area/thickness. Предложение: перед нормализацией time_point проверять исходное число и единицу по источникам результата; неподтверждённое время не использовать как установленное условие измерения. Добавить тест на выдуманное время и положительный тест с настоящим evidence.

## Статус предыдущего ревью

- Запрет redirects реализован через `NoRedirect`, проверяются cross-origin и downgrade.
- Число проверяется и в fragment, и в исходном source; знак, обрезанная подстрока, диапазоны и неопределённость учитываются.
- Для единиц добавлена буквальная проверка источников; старый пример `1000 mV → 1000 V` больше не нормализуется при единственном исходном source.
- Дубликаты с пустыми normalized-полями теперь сравниваются по raw и статусу.
- Bandgap/area/thickness и light_intensity проверяются по evidence. Абсолютный spread пересчитывается и сохраняется в note; оставшийся случай relative spread описан выше.

## Что хорошо

- Scripts не фабрикует сущности и не вызывает API; auto/model не маскируют отсутствие клиента или ошибку API успешным offline-ответом.
- Профиль и его hash входят в результат; generic evidence привязано к отдельным полям, solar честно помечает record-level evidence.
- Неизвестное, неподтверждённое и inferred для boolean/reference не объявляются доказанным отсутствием или полной научной верификацией.
- Бюджет запроса проверяется до model_client, без молчаливого усечения документа.
- CSV сохраняют объявленные колонки и для пустых online-таблиц; staging защищает от частично записанного комплекта.
- Есть полезные негативные регрессии по источникам, FK, transport, нормализации и атомарности. Основной пробел тестового маршрута — scripts + fields profile + export.

### Блокер solar на момент второй проверки (закрыт ниже)

- 🔴 `solar_facts.py:271–279` — для `raw_unit="%"` явно отключён запрет процентного relative spread. Источник `PCE = 20 % (relative uncertainty ±2%)`, `raw_value="20"`, `raw_unit="%"`, `spread_value="2"` проходит и экспортирует spread `2` рядом с `20 %`, то есть два процентных пункта вместо относительных 2% (0.4 процентного пункта). По выбранному контракту относительную/неоднозначную неопределённость нужно вообще оставлять только в note. Это не требование научного scorer: источник явно говорит `relative`, но локальный normalizer выдаёт абсолютный spread. Предложение: для процентных метрик также отсеивать явно relative и неоднозначные выражения; не считать совпадение единицы `%` достаточным доказательством абсолютной шкалы. Добавить эту регрессию, сохранив положительный тест однозначного абсолютного spread.

## Независимое ревью evaluator

Diff: целиком прочитаны новые `evaluate_extraction.py`, `test_evaluate_extraction.py` · Первоначальный вердикт: ⚠️ после правок 🔴; закрытие ниже.

Проверка ограничена заявленной policy: mention-level basic/context multiset, конечные числа, разрешение локальных device/measurement IDs, abstention, selection, micro/macro и отдельный scope. Полная научная эквивалентность, PDF/quote verification и расширение context не требуются. Сообщённые 18 passed и gold-self 626 TP самостоятельно не воспроизводились. Ниже только блокирующие дефекты, не пожелания к расширению scorer.

### Находки

- 🔴 `evaluate_extraction.py:24–31,179` — конечность входных Decimal не гарантирует корректность арифметики tolerance: вычитание и `abs` выполняются в стандартном контексте с precision=28. Например, predicted `1`, gold `-1e-40`, tolerance `1` дают округлённую разность `1` и ложный TP, хотя точная разность больше допуска. На принятом конечном `1e1000000` при ненулевом tolerance вычитание может выбросить `decimal.Overflow`, который CLI не перехватывает. Policy обещает finite Decimal comparison и maximum-cardinality по допуску, но фактическое отношение близости другое. Предложение: ограничить поддерживаемые точность/экспоненту на входе и вычислять разность в достаточно точном `localcontext` без потери значимых разрядов либо использовать точное сравнение с допуском другим способом. Неподдерживаемые числа отвергать `ValueError` до matching. Добавить обе регрессии и тест на точную границу допуска.

- 🔴 `evaluate_extraction.py:306–309` — вывод не атомарен при ошибке записи: `"x"` защищает от перезаписи, но сразу создаёт окончательный `report.json`. При частичной записи/ошибке flush (например, disk full) остаётся обрезанный файл, CLI завершается ошибкой, а повторный запуск отказывается работать из-за существующего output. Тест `test_cli_and_no_overwrite_or_partial_output_on_validation_error` проверяет только ошибку до открытия файла и этот сценарий не покрывает. Предложение: сначала записать и закрыть временный файл в том же каталоге, затем публиковать его атомарно **без замены существующего назначения**, очищая staging при ошибке. Добавить fault-injection на write/close и проверку отсутствия итогового файла после неудачи; сохранить тест no-overwrite.

### Что хорошо / проверенные границы policy

- IDs индексируются парой publication + local ID; одинаковые локальные IDs разных статей не смешиваются. Результат разрешает ссылки в своём bundle, а между bundles сравниваются описательные поля, не IDs.
- Повторы считаются отдельными mentions без повторного использования gold; exact matching использует Counter. Двухуказательный matching отсортированных значений корректен для единого абсолютного допуска, если арифметика сравнения точна.
- Пустые normalized-поля исключаются как abstention; нормализованный gold при этом остаётся FN. Непустые NaN/Infinity проверяются до исключения по пустой единице.
- Selection, отсутствие prediction для gold-публикации, отдельный scope и micro/macro соответствуют явно записанной policy. Пустые статьи сознательно остаются в macro с нулевыми знаменателями.
- Тесты покрывают разные IDs, мультисеты, selection, scope, abstention и нечисловые значения; self-evaluation полезен как smoke test, но не проверяет два описанных failure paths.
