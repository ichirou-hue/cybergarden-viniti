## 🟡 Стоит исправить

### 🟡 S1. `_bandgap` теперь может приписать поглотителю bandgap буферного слоя

`solar_offline.py:1216-1220`. Фильтр `WIDE_GAP` больше не отбрасывает
`wide bandgap` безусловно: значение принимается, если в окне `match.start() - 60 ..
match.end() + 60` встретилось слово `absorber` или напечатанная формула материала.
Окно в 120 символов почти всегда содержит имя поглотителя, даже когда фраза о
широкозонном соседе. Замер прямыми вызовами:

```
_bandgap({'1': 'The CIGS absorber was combined with a wide bandgap Zn(O,S) buffer of 3.2 eV.'}, 'CIGS')
  -> ('3.2', '1', 'bandgap Zn(O,S) buffer of 3.2 eV')
_bandgap({'1': 'The absorber stack used a wide bandgap CdS window layer of 2.4 eV.'}, 'CIGS')
  -> ('2.4', '1', 'bandgap CdS window layer of 2.4 eV')
_bandgap({'1': 'A wide bandgap CuCrOx buffer of 3.2 eV was deposited on the CIGS absorber.'}, 'CIGS')
  -> ('3.2', '1', 'bandgap CuCrOx buffer of 3.2 eV')
```

То есть CIGS с Eg 1.15 eV может получить в `materials.bandgap_value` 3.2 или 2.4 eV.
До правки такие фразы отбрасывались. На `_corpus/area1/dev` регрессии пока нет: я
прогнал старую и новую `_bandgap` по всем 21 PDF, значения совпали везде. То есть
это не блокер, но правило в текущем виде ловит обычную формулировку «поглотитель +
широкозонный буфер», а таких фраз в корпусе будет много.

Предложение: не смотреть на всю фразу, а требовать, чтобы `wide bandgap` относился
к тому же имени, что и `absorber`/материал (например, обрывать окно на
`buffer|layer|window|ETL|HTL|contact`), либо принимать `wide bandgap` только когда
число стоит вплотную за именем поглотителя. Тесты на перечисленные фразы с ожиданием
пустого значения.

### 🟡 S2. Кэш `SolarStore` не учитывает ревизию экстрактора

`solar_api.py:204-207`: `ingest` ищет документ только по `content_hash` и на
попадании сразу возвращает сохранённый summary, вместе со старым
`handler_revision`. Правило проекта - «поменял извлечение, подними ревизию»
(`AGENTS.md:292-299`), и `batch --resume` его соблюдает, а веб-каталог нет: после
поднятия `solar_version.PARSER_VERSION` сайт продолжит показывать цифры старой
версии. Это та же ловушка, что описана для `library.py:71`.

Предложение: при попадании сравнивать `json.loads(old["summary"])["handler_revision"]`
с `solar_version.PARSER_VERSION` и переразбирать при расхождении (или хранить
ревизию отдельной колонкой); тест «те же байты, другая ревизия».

### 🟡 S3. Исключённая статья выглядит как неудачный разбор

`solar_api.py:173-175` добавляет предупреждение «Результаты не найдены:
детерминированный экстрактор не извлёк подтверждённых строк», а `solar_api.py:183`
ставит `status: "partial"` всякий раз, когда результатов нет. Для `D006`
(`in_scope=false`, `exclusion_reason='Моделирование или теория без изготовленных
приборов.'`) конверт получается таким:

```
status partial, counts {'results': 0, 'issues': 0}
publication.in_scope 'false'
warnings: ... 'Результаты не найдены: детерминированный экстрактор не извлёк подтверждённых строк.'
```

`static/document.js:202-206` на `partial` рисует «Обработано частично / Часть
страниц не разобрана». Статья при этом разобрана полностью, просто выведена из
области по правилу. Дополнительно `static/document.js:157` делает
`Boolean(publication.in_scope)`, а `in_scope` приходит строкой `"false"`, то есть
бейдж пишет «в области» для исключённой статьи.

Предложение: в `_envelope` учитывать `in_scope == "false"`: не добавлять
предупреждение про «не извлёк» и отдавать отдельный статус (или `done`).
Приведение `in_scope` к bool в конверте менять не стоит: это поле шаблона и оно же
уходит в `export.json`. Бейдж правится в `static/document.js` - файл общий, правку
согласовать с владельцем фронтенда.

### 🟡 S4. Вкладка «Фрагменты PDF»: дубли прозы и потерянные типы источников

Маршрут `/sources` для solar теперь идёт через общий помощник RAG
(`server.py:842`, `rag_api.sources`, `rag_api.py:846-881`). Он подходит конверту
solar не полностью: на `D001`, `D003`, `D004` это видно.

```
D004  GET /sources -> total 1253, уникальных source_id 1250, повторяются 33, 39, 139
D003  GET /sources -> total 1016, уникальных source_id 1000, повторяются 16 id
D001  GET /sources -> total  394, уникальных source_id  387, повторяются 7 id
D004  GET /sources?kind=caption  -> 0   (в text_sources 7 подписей)
D004  GET /sources?kind=equation -> 0   (в text_sources 3 формулы)
```

1. `rag_api.py:850-861` дедуплицирует только источники из `results`, а
   `rag_api.py:869-879` добавляет `text_sources` без проверки `seen`. Так как
   `solar_api._text_sources` (`solar_api.py:108-115`) отдаёт все нетронутые
   источники, включая те, что уже анкорят результат, один и тот же фрагмент
   показывается дважды с двумя одинаковыми кнопками «Стр. N»: на `D004` таких пар
   3, на `D003` 16, на `D001` 7. Это прозаические якоря результатов; табличные не
   дублируются, потому что `_text_sources` их отбрасывает.
2. `rag_api.py:876` жёстко ставит `"kind": "text"` для `text_sources`, поэтому типы
   `caption` и `equation`, которые есть в конверте (`solar_api.py:113`) и в
   селекторе `static/tracks/solar.js:19`, до интерфейса не доходят: выбор «Подпись»
   или «Формула» показывает «Фрагменты не найдены». В списке подписи и формулы
   подписаны как «Текст».

Предложение: в `rag_api.sources` проверять `seen` и для `text_sources`, а тип брать
из самого источника (`source.get("kind")`), подставляя `table` только когда тип не
задан. Правка общая с RAG, поэтому нужен прогон `tests/test_rag_api.py` и
`test_solar_api`.

Заодно: новый тест `test_solar_api.py:206-217` (`test_sources_endpoint_includes_text_sources`)
закрепляет дубль как ожидаемое: для конверта с одним источником он требует ровно две
записи с одним и тем же `source_id` 7. После исправления тест придётся поменять на
`len(...) == 1`.

### 🟡 S6. Два теста в `test_solar_api.py` проходят при сломанном коде

HTTP-маршруты теперь покрыты (`DocumentApiTest`, `test_solar_api.py:157-238`), и это

   проверить сообщение или поставить `mock.patch.object(solar_offline, "extract_pdf")`

## Новые находки этого раунда

### 🟡 R1. Смена ревизии при другом имени файла оставляет вторую строку и старый конверт

`solar_api.py:248-253` на расхождении ревизии честно переразбирает PDF, но `document_id`
строится из имени файла (`solar_api.py:255`), а запись идёт `INSERT OR REPLACE` по
`document_id` (`solar_api.py:267`), без удаления старой строки по `content_hash`.
Проверил сценарий «те же байты, другое имя, старый кэш»:

```
первая загрузка A.pdf         -> solar:a-05f64beb
старый кэш (revision 1)
загрузка B.pdf (те же байты)  -> solar:b-05f64beb, revision 2
строки в таблице              -> ['solar:a-05f64beb', 'solar:b-05f64beb']
list() для каталога           -> две карточки одного PDF
SELECT по content_hash        -> solar:a-05f64beb, revision 1
```

Последствия: в каталоге дубль; закладка на старый `document_id` навсегда отдаёт старый
конверт; выборка по хэшу возвращает старую строку, поэтому каждый следующий `ingest`
тех же байт снова тратит разбор. Тест `test_cache_from_an_older_revision_is_reparsed`
проверяет только совпадающее имя и потому это не ловит.

Предложение: на расхождении ревизии удалять строку по `content_hash` (или брать ключ
из хэша, а имя держать только в summary), тест с переименованным файлом.
