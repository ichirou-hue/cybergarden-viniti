## Находки

- 🔴 `solar_extract.py:90–95` — стандартный `urlopen` автоматически следует HTTP redirect, а `Authorization`, заданный через `Request(..., headers=...)`, может переноситься на другой host; стандартный redirect handler допускает также HTTPS → HTTP. Фиксированного исходного ENDPOINT недостаточно для гарантии «ключ только OpenRouter». При ответе 302/303 с чужим `Location` ключ уйдёт следующему получателю, хотя сам запрос станет GET. Предложение: для этого клиента запретить redirects собственным `HTTPRedirectHandler` (проще и безопаснее), либо строго разрешать только тот же HTTPS origin без downgrade. Проверять redirect до отправки следующего запроса, не только `response.geturl()` после. Добавить тесты cross-origin и HTTPS → HTTP с утверждением, что второго запроса с ключом нет.

- 🔴 `solar_facts.py:104–115` — проверка границ числа действует только внутри предложенного моделью фрагмента, а сам фрагмент проверяется простым substring. Поэтому для локального source `"PCE = 116 %"` кандидат `source_fragment="16"`, `raw_value="16"`, `raw_unit="%"` проходит и нормализуется в 16. Даже с полной цитатой `"Jsc = -2 mA/cm2"` кандидат `raw_value="2"` проходит: знак не входит в запрещённую левую границу regex. Таким образом, обещанная защита от подстрок числа обходится, отрицательное значение может превратиться в положительное и не попасть в `range`. Предложение: проверять позицию полного числового токена в исходном локальном source, сохраняя знак и числовое окружение за границами fragment. Добавить отрицательные тесты на обрезанный fragment, потерянный знак и выбор только части диапазона/выражения с неопределённостью.

- 🔴 `solar_facts.py:188–196` — единица модели используется как достаточное основание для пересчёта, хотя никакой evidence для неё не проверяется. На существующей fixture достаточно заменить у Voc `raw_unit="mV"` на `"V"`: цитата по-прежнему содержит `1000 mV`, но экспорт выдаст `1000 V`. Для FF из цитаты `0.8 fraction` замена на `%` даст `0.8 %`. Это не просто неопределённая научная связь, а принятие явно противоречащей источнику шкалы. Глобальное предупреждение в `finalize` не предотвращает ложное `normalized_value`. Предложение: добавить проверяемый источник единицы/шкалы (включая отдельный заголовок таблицы), разрешать пересчёт только при подтверждённом соответствии числу; при неподтверждённой или противоречивой единице сохранять raw, оставлять normalized пустым и создавать issue. Тестировать неверную единицу, явную долю и единицу в отдельном header-source.

- 🔴 `solar_facts.py:272–279` — разные ненормализуемые значения признаются одинаковыми дубликатами: после `normalize` у обоих пустые normalized-поля. Например, две строки одного PCE/устройства/измерения с `raw_value="16 ± 1"` и `"20 ± 1"` и соответствующими реальными цитатами проходят при `duplicate_of`, поскольку контекст совпадает и `"" == ""`. Аналогично проходят разные числа с неизвестной единицей; extraction_status тоже не сравнивается. В дальнейшем потребитель может исключить противоречащую запись как повтор. Предложение: для duplicate требовать совпадающий статус и доказанное равенство значений: сравнивать нормализованные значения только когда оба действительно получены; иначе сравнивать полные raw_value/raw_unit после безопасной текстовой нормализации либо отклонять неоднозначный duplicate. Добавить тесты на разные диапазоны/неопределённости, неизвестные единицы и разные статусы.

- 🟡 `solar_facts.py:194–196` — нормализация изменяет единицу metric_value, но оставляет `spread_value` без пересчёта и без указания исходной единицы. Для среднего Voc `raw_value="1000"`, `raw_unit="mV"`, `spread_value="20"` CSV получится `metric_value=1`, `metric_unit=V`, `spread_value=20`: численно это уже неверный разброс рядом со значением в V. В шаблоне отдельного spread_unit нет, prompt не определяет, в какой шкале модель должна вернуть spread. Предложение: явно задать spread в исходной единице и применять тот же коэффициент, сохраняя исходный spread в note/sidecar; если это относительный или неоднозначный разброс, не выдавать его как абсолютный нормализованный. Добавить тест `1000 ± 20 mV → 1 ± 0.02 V` и процентной относительной неопределённости.

- 🟡 `solar_facts.py:97–99,197–213` — для числовых полей сущностей достаточно ссылки на любой существующий source, наличие самого числа вообще не проверяется. Например, в fixture изменение `bandgap_value` с `1.5` на `0.9` при неизменном source `Eg 1.5 eV` принимается; `test_solar.py:136–138` прямо закрепляет этот случай. Выдуманное значение затем не только экспортируется, но и порождает `voc_limit` для реального Voc. Аналогичны active_area и layer_thickness. Предложение: перед нормализацией этих трёх scalar-полей проверять исходное число и единицу в привязанном evidence; неподтверждённое поле блокировать либо оставлять лишь в диагностике, не использовать в физических проверках. В тесте voc_limit менять также локальный source; отдельно проверить отказ на выдуманный bandgap.

## Что хорошо

- Независимый CLI переиспользует PDF extraction и не затрагивает существующий backend.
- Строгие типы CSV-полей, проверка source IDs (включая запрет bool), страниц, FK, принадлежности measurement/device и циклов duplicate_of.
- Cited-результаты не могут иметь собственные device/measurement и не включаются в J–V tuple.
- Model-computed normalized-поля отбрасываются; неоднозначный raw не сводится нормализатором к центральному числу.
- J–V проверяется только при заданной интенсивности и уникальном наборе метрик одного контекста; формула и коэффициенты основных единиц корректны.
- Лимиты размера PDF/ответа, bounded retries, скрытие provider error bodies, отказ на усечённый ответ, prepare без API.
- Экспорт сериализуется в staging-каталог до публикации комплекта; тесты покрывают ошибку сериализации и существующий output.
- Тесты покрывают важные негативные случаи. Для перечисленных находок нужны дополнительные регрессионные тесты, а не расширение среза до полноценного продукта.
